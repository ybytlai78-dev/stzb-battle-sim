## 0. 这套工具要回答的三个问题

1. 某个输出武将**换一个战法 / 换一个队友**，最终伤害怎么变？
   → L1 单次伤害曲线（数学层）→ L2 回合期望曲线（期望层）→ L3 组合搜索（最优解）。
2. **前三回合总伤怎么最大化**？整局 8 回合呢？（两个答案不同，见 §3.3）
3. 一支队伍**实战胜率**多少、靠什么赢（斩首 / 兵力判定），**防御体系怎么选**？
   → L4 走真引擎的批量模拟。

## 2. 四层口径（用户已逐条确认）

### 2.1 L1 单次伤害模型

- **数值完全复用引擎**：`calcDamage` / `buffMult` / `attrFactor`（`src/engine/formulas.ts`），与实战同一套公式，不做二次近似。
- **X 轴（换因变量）**：兵力、攻击、攻击差、防御、谋略、目标谋略、发动率、增伤、减伤、目标数（`X_AXES`）。
- **Y 指标**：期望伤害 / 区间带 / 三段拆分（兵力基础 + 属性基础 + 主要伤害）/ 相对增量 / 边际（`Y_METRICS`，`band`/`parts`/`delta`/`marginal`）。
- 曲线：默认 5 条、最多 6 条（`CURVE_COLORS`）；参数系数 10 档（`COEFF_STEPS`）。

### 2.2 L2 伤害期望模型 —— 主口径：真引擎模拟测评（2026-09-28 起）

> **口径（用户 2026-09-28，勿再询问）**：L2 是**伤害期望模型**，核心目的是「算出这支队伍带哪些战法伤害期望最高」；
> **胜负 / 胜率 / 兵力优势是 L4 的事，L2 不掺**。期望来源 = **实际模拟**（`runBattle`），不再用解析式。
> 靶子只有**不还手的木桩**（要求 1）；**用户指定的战法原样保留**，只填空槽（要求 2）。

- **排序口径 = 核心将的伤害期望**（用户 2026-09-28 二次定稿，**不是全队总伤**）：只统计核心将打出的伤害，可多选（求和）；
  核心将缺省自动识别（主战法带对敌伤害段 / DoT 且「攻击 + 谋略」最高者），页面上也可按槽位勾「核心位」覆盖。
  为什么不用全队总伤：**辅助战法的强度不随施法者属性变**——实测同一个「计险远近」放太史慈 / 曹植 / 陆抗都是 44,699（差异 0.0%），
  「大赏三军」1.8%、「长兵方阵」4.8%；总伤口径对「辅助战法放谁」几乎无感 → 大量完全并列 → 搜索按 DFS 顺序随手挑一个，
  就会出现「主C带辅助、辅助带输出」。换成核心将口径后，输出战法只有放在核心将身上才涨目标，定位自然落位。
  全队总伤仍会展示（参考列），但不参与排名。
- **参与匹配的将**（对齐 L3 优化器的 `unitIdxs`）：勾选哪些将参与搜索，**缺省 = 自动识别的核心将**；
  其余将的战法原样保留、一个都不动（用户自己配的防御体系战法不会被搜掉）。
- **靶子 = 不还手的木桩 ×3**：不放战法、不普攻（引擎 `BattleConfig.inertSides = ['enemy']`），只挨打；
  属性取面板「目标防御 / 目标谋略 / 目标兵种」，单只兵力 `dummyTroops`（默认 **150000**）。
  我方打在木桩身上的 **DoT / 「目标下次行动前」延迟伤害照常结算**（引擎出口放在 DoT 之后）。
  - 伤害公式不看目标兵力（只有 `Math.min(伤害, 剩余兵力)` 的截断）→ 给足兵力只为「打不完」；被截断会
    在结果里报 `wipedRuns` / `wipedCombos` 提醒调大。
  - 木桩不行动 ⇒ 依赖「敌军已行动」的机制（缓师徐持等）不会触发，属预期口径。
- **三阶段（阈值都可配置）**：
  - ① **逐将粗筛**：**单槽将** = 每个候选战法在「基线配置 + 该槽放该战法」上真跑 `coarseRuns`（默认 **3**）场；
    **双槽将 = 按成对组合评估**（用户 2026-09-28 口径）：先跑一圈单挂拿到「搭子基准」（前 `pairCarriers`，默认 10），
    再用基准 × **全部候选**两两配对各跑 `coarseRuns` 场。为什么要成对：「击势」这类增伤战法要**带满槽**才有收益，
    只看单挂成绩会在这一关被误杀（实测成对后它进了该将前十里的 5 对）。每将保留前 `unitKeep`（默认 **32**）个选项，
    双槽将还留最多 3 个「单挂」选项当出口；
  - ② **组合粗筛榜单**：各将选项拼成整队组合（守**全队战法唯一**）后，每个组合真跑 `coarseRuns` 场 → 按口径值排**榜单**
    → 前 `coarseTop`（默认 **32**）**支不同战法**进决赛；组合过多时按各将名次优先展开，上限 `maxCombos`（默认 1000，截断会报 `combosCapped`）；
  - ③ **决赛排行**：每支组合真跑 `finalRuns`（默认 **20**，**低于 20 一律抬回 20**）场 → 汇总伤害期望并排行。
- **「不同战法套」去重**：换将 / 换槽的排列在本引擎里常打出**完全一样**的结果（实测如此），若按名次取会让决赛名额
  浪费在排列重复上 → 同一套战法只保留成绩最好的一种排法，其余标 `duplicateOf`（榜单里显示「同套（与第 N 名）」）。
- **候选口径**：**只填空槽**——用户已指定战法的槽位原样保留、不进候选池（可以先把空槽改成自定义防御体系战法再评测）；
  候选池缺省 = 全部可学战法 − 队内已占用（解析模型当年为「未建模字段」踢出严格池的那批，模拟器不需要建模）；
  空槽宽度取 `max(SKILL_SLOTS, skillIds.length)`（截图识别的配置是 `[主战法, 可学, 可学]`，只看前 2 格会漏掉最后一格）。
- **期望输出**：`FinalRow`（`web/simExpectation.ts`）——`mean / meanFirst3`（**口径值 = 核心将伤害**）、`meanTotal`（全队总伤，参考）、
  `sd / halfWidth / min / max / median / byUnit（带 core 标记）/ bySkill / wipedRuns / coarseMean / coarseBias / analyticTotal / deltaTotal`（**无胜负字段**）。
- **自检与对照**（都在结果里出数）：① 同组合「粗筛 `coarseRuns` 场」vs 决赛 `finalRuns` 场的偏差 + 排序成对一致率
  （`rankAgreement`）→ 3 场只能淘汰；② 木桩截断自检；③ 旧解析值对照（解析按抽象目标模板算，仅历史参考）。
- **复现**：种子 = `baseSeed + 场次`（同一场次的种子对所有候选一致 → 配对比较），奇数场交换场地（木桩视角随交换翻转）。
- **实现入口**：`simSlots` / `candidateSkills` / `autoCoreUnits` / `legalCombos`（按「将选项」DFS 守全队唯一；保留名单拼不出组合时
  放开到全量选项并标记 `comboFallback`）/ `simExpectationSteps`（**生成器，每真跑一场 yield 一次**；同步 `runSimExpectation`、页面
  `runSimExpectationAsync` 分片让出主线程）/ `estimateBattles`（开跑前估场次，含配对阶段）；视图纯函数在 `web/simExpectView.ts`。
- **页面**：`/round-model.html` 的「模拟测评」区（参数 + 进度 + 逐将粗筛表「双槽将显示成对组合」 + 组合榜单 + 决赛排行
  + 每将/每战法折叠明细 + 口径提示）；配置改动后结果标「过期」。
- **离线**：`npx tsx scripts/sim_expectation.mts`（默认拿队伍集的我方队当待测队伍，**清出核心将的全部可学槽（最多 2 格 → 走成对评估）**，
  其余将原装不动），报告写 `docs/L2模拟期望测评报告.md`；`--match 0,1,2` 放开搜索范围，`--core 2` 指定核心将，`--core all` 回全队总伤口径，
  `--keep/--paircars/--top` 分别对应每将保留 / 配对基准 / 进决赛支数。
- **实跑基线**（2026-09-28，脚本默认参数 = 只搜核心将的两个可学槽）：
  我方·SP太史慈曹植陆抗，自动识别核心将 = **陆抗** → 只搜陆抗·槽2+槽3（成对）：**8062 场 / 57s**；2218 个成对组合 →
  32 支进决赛（20 场/支）；榜首 **陆抗·危崖困军 + 计险远近**（核心将期望 26,500 ±1,675，全队总伤 74,636）；
  3 场粗筛 vs 决赛排序一致率 73%；无组合把木桩打空。玩家原装（青囊秘要 + 浑水摸鱼）没进前十。
  口径对照（全队三将都搜、`--match 0,1,2`）：**全队总伤口径**会让核心将拿辅助（陆抗·知己知彼）；
  **核心将口径**则是核心将拿输出（陆抗·三术奇谋），两者全队总伤几乎一样（82,430 vs 82,358）。

**解析式模型（`web/roundModel.ts`，仍是 L3 的代价函数）**：

> **口径（用户 2026-09-22 确认，已于 2026-09-28 降级为对照）**：**只算回合期望**——不含控制、规避、兵力截断、目标阵亡。

- 战法 → `ParsedSkill`（`parseSkill(skill, morale, ctx)`）：段、DoT、概率、窗口、缩放属性。
- 窗口：`RoundWindow` / `inWindow` / `windowTotals(result, n)` → **前 3 / 前 N / 整局 8** 随意切。
- 关键函数：`preparedCastProb`（准备战法）、`dynamicRateSeries`（二类指挥动态发动率）、`stackLayers`（叠层）、`chainExtraRepeats`（战法链）、`expectedFirstRound`、`effectiveRate`（**`chance × moraleRate`，士气修正**）。
- 输出：逐回合期望表 + `SOURCE_ORDER`（普攻/追击/主动/准备/一类指挥/二类指挥/被动/持续伤害）来源堆叠图 + 未建模告警。
- 页面带 error boundary（`mountRoundModel` 包 `mountRoundModelInner`），出错显示在页上而不是白屏。

### 2.3 L3 组合优化 · **优化武将（队友）**——真引擎模拟测评（2026-09-28 起）

> **分工（用户 2026-09-28 口径，勿再询问）**：**L2 = 优化战法**（把「空战法槽」当搜索维度：这支队伍带哪些战法伤害期望最高）；
> **L3 = 优化武将**（把**队友位**当那个空槽，对**队友组合**做粗筛：围绕核心将配哪两个队友）。
> 两层的靶子（不还手木桩）、排序口径（核心将伤害期望）、三阶段阈值（粗筛 3 场 → 决赛 ≥20 场）**完全一致**，
> 所以「先用 L3 选队友 → 再切 L2 配全队战法」两步可以叠加，不换尺子。

- **页面**：`/optimize.html`（`web/optimizeView.ts` + `web/optimize.css`）——**L2 / L3 双模式页**：
  **左栏配置面板只渲染一份（`renderConfigPanel`），两个模式共用并同步**，切模式只换右侧那块；
  两个模式各自保留自己的参数与结果（切来切去不丢），配置一改结果标「过期」。
  旧的 `/optimizer.html`（解析口径）保留，页头给了指向 `optimize.html` 的链接。
- **搜索维度 = 队友位**（`web/simMate.ts`）：核心位（排序口径）固定不动，其余位才是候选队友位。
  - 勾 **1 个**队友位 → 单槽粗筛：每个候选武将在该位真跑 `coarseRuns` 场；
  - 勾 **2 个**队友位 → **成对评估**（用户口径，同 L2 双槽成对）：先跑一圈单挂拿「搭子基准」（每个位各取前
    `pairCarriers` 名），再用「基准 × 全部候选」两两配对真跑——**两个位各作一次基准方向**，所以
    「谁站大营 / 谁站前锋」两种排法都会评到，不会被系统性偏袒；另留最多 3 个「单挂」选项（只换一个位、另一位保持当前武将）当出口。
    理由同 L2 的击势：队友是**互相成就**的（辅助要配得上输出将、双辅助会互相挤占），只按单挂成绩独立筛会把「只有搭在一起才强」的组合误杀。
- **候选武将口径**：池 = 上架武将池（缺省）/ 含下架（可选）− 队内已上阵武将（含核心与未匹配的队友）
  − **与「不参与匹配的将」互斥的武将**；候选进场时：**等级沿用被替换的槽位**、加点清零、兵种取本体、不带宝物 / 兵系特性、**战法槽清空**。
  清空是因为**战法由 L2 那一步配**（L2 只填空槽）——故 L3 的所有试跑都在「匹配位战法槽已清空」的基线上做，
  它是 L3 交给 L2 的起始状态；对照基线 = 当前队友 + 同一清空状态（结果区显示榜首比它高多少）。
- **同队互斥必须先剔掉（用户 2026-09-28 实测卡点）**：引擎 `runBattle` 在开打前做互斥校验，同 `mutualExclusionGroup`
  的武将同队直接抛「配队非法：互斥冲突」——现只有 **赵云 ↔ SP赵云**、**姜维 ↔ SP姜维** 两组（其余同名武将如关羽蜀/魏可同队，
  口径见 `src/data/hero-utils.ts` 与 `tests/mutual_exclusion.test.ts`）。
  跑批是几十分钟的长任务，**一遇到「核心将带赵云 + 候选 SP赵云」就整轮作废**（用户实测就是这么卡住的）。故 L3：
  ① 候选池先剔掉与固定将互斥的（结果里报 `poolSkippedMutual`，页面写「互斥剔除 N」）；
  ② 成对 / 单挂 / 组合 / 决赛每次都过 `cfgHeroesLegal`（不重复 + 无互斥），撞组的跳过并计入 `skippedIllegal`；
  ③ 当前配置本身就违规时不跑基线、标 `baselineIllegal`（页面红字让用户先改左栏），而不是抛错；
  ④ 真跑仍包一层 try/catch，异常记进 `errors` 并跳过该项（引擎以后再加规则也不会把整轮跑批带走）。
  口径提示里「同队互斥已剔掉」那一条**在没有任何决赛结果时也照常显示**（那正是最需要看到提示的时候）。
- **三阶段**：① 队友位粗筛（单挂 / 成对）→ ② **组合粗筛榜单**（按「不同武将套」去重：同两位武将换个站位算同一套，
  只留成绩最好的排法）→ ③ 决赛排行（`finalRuns` 场，**低于 20 一律抬回 20**）。
- **排序口径**：**核心将伤害期望**（同 L2，可勾核心位 / 多选取和；全队总伤只作参考列）。木桩不还手的边界照旧：
  **防御 / 控制型队友的价值量不出来**（这是「伤害期望」口径的边界，胜率与防御体系看 L4）。
- **输出与自检**（`MateSimResult`）：`groups`（逐位粗筛，成对模式 = 有序对榜）/ `combos`（组合榜单 + `heroKey` 去重）/
  `finals`（`mean / sd / halfWidth / min / max / median / byUnit / bySkill / wipedRuns / coarseBias`）/
  `baseline`（对照基线）/ `battles`（真跑场次）/ `rankAgreement`（粗筛 vs 决赛排序一致率）/ `wipedCombos`。
- **复现**：种子 = `baseSeed + 场次`（同一场次对所有候选一致 → 配对比较），奇数场交换场地；`estimateMateBattles` 开跑前估场次。
- **应用（两步衔接）**：决赛每行有「应用」——武将写进左栏对应的队友位 + **该位战法槽清空**；
  应用后摘要卡给「→ 去 L2 优化战法」按钮（切模式的入口之一），L2 侧直接用同一份配置填空槽。

**旧解析口径（`/optimizer.html`，保留）**：

- 目标：给定武将，搜「带什么战法 + 配什么队友」在**指定口径**下总伤最大。
- 算法：beam search——生成器 `searchLoadoutsSteps`（可报进度）/ 同步 `searchLoadouts`；队友搜索 `searchTeammates`；`makeEvaluator(cfg, objectiveRounds)`。
- **合法性必须遵守（引擎级约束）**：
  - 候选池只含**可学习战法**（主战法不进池，`LEARNABLE_SKILL_IDS`）；
  - **全队战法唯一**：同一战法不得出现在任意两名武将、任意两个槽位（`usedAnywhere`）；
  - 每将 2 个战法槽（`SKILL_SLOTS = 2`）。
- 候选池档位 `candidatePool(morale)`：`strict`（严格池 = 有贡献 + 已上架 + 无未建模字段）/ `contributing`（有贡献）/ `all`；被排除项带原因（`unmodeledNotes` / `approximationNotes` / `isFullyModeled`）。**严格池现 92 个**（起点 36）；剩下的排除项 = 数据侧未上架 + 单点机制未建模。
- `charges`（次数上限类）**故意算未建模**——不做「整场有效」的假近似，宁可把它排除在严格池外。

### 2.4 L4 实战胜率批量模拟

- **走真引擎 `runBattle`**，不是解析模型 → 含控制 / 规避 / 兵力截断 / 阵亡 / 伤兵池。
- **胜负判定**（`judgeOutcome`）：引擎是斩首制（大营阵亡 → `win`/`loss`）；打满 8 回合 `draw` → **比双方剩余兵力比例，高者胜**。UI 把胜场拆成「斩首胜 / 兵力判定胜」。
- **主指标**：**胜率（±95% 置信半宽）+ 平均剩余兵力优势**（我方剩余% − 敌方剩余%）。
- **样本标准（用户定）：500 场/对局**为默认口径（UI 可选 100 / 200 / 500 / 2000）。
  - 固定种子：`runOne(..., index, env)` 用 `env.baseSeed + index` → 同配置**可复现**；`DEFAULT_ENV = { maxRounds: 8, swapSides: true, baseSeed: 20260922 }`。
  - **奇数场交换场地**（`swapSides`），消除左右位偏差。
  - 性能：约 3.2 ms/场 → 500 场 ≈ 1.6 s。页面用 `runBatchAsync`（每 25 场让出主线程）+ 进度条。
- **统计口径**（`BatchStats`）：
  - 伤害占比 `damageShare` = 我方伤害 ÷ 双方总伤害；
  - **控制口径 = 平均控制回合数（人回合）**（`controlMine` / `controlEnemy`，`CONTROL_STATUSES` = 混乱/暴走/怯战/犹豫）；
  - **恢复口径 = 恢复兵力占比**（`healShare`），另给双方场均治疗（`avgHealMine` / `avgHealEnemy`）;
  - 每将平均伤害/承伤/治疗/被控（`perUnit`）+ 每战法平均释放/伤害/控制/恢复（`perSkill`）→ 各战法伤害饼图。
- **对手侧（用户选定）**：多路径对手——① 截图识别队伍配置（**待做，见 §5**）② 手动指定并配战法；两者都可**备注名进对手池**、随时切换。对手池持久化 `localStorage['dsh-battle-sim-opponents-v1']`。
- 页面**不渲染战报正文、只看统计**（真引擎跑 8 回合，只出胜率 / 占比 / 成员饼图；单场过程要看就回主站战报）。

**实测例**（吕布/貂蝉/刘备 vs 甘宁/孙策/貂蝉，500 场）：
胜率 **93.6% ±2.1%**，468 胜 / 0 负 / 32 平（斩首 266 + 兵力判定 202），兵力优势 **+40.2**，
伤害占比 73.9%，控制 3.91 vs 1.52 人回合，恢复 3,578 vs 0。

## 3. 关键结论（别再重复推导）

### 3.1 引擎数据修正：18 处 `damage_boost` 补 `damageType`

物理武将的候选池里「深谋远虑」登顶，而它只加谋略伤害——**根因不是模型错，是引擎数据缺 `damageType`**。
按官方描述逐个核对后补 18 个（物理 14 / 策略 4），另 7 个本来就有过滤：

- 策略：`shenmou_yuanlv` 深谋远虑、`fengsheng_heli` 风声鹤唳、`jieliang` 劫粮、`kaolao` 犒劳
- 物理：`xuejian_huangsha` 血溅黄砂、`hubao_dujun` 虎豹督军、`lingming_fuchen` 令明负榇、`jinguo_zhanzhen` 巾帼战阵、
  `guoshi_wushuang` 国士无双、`yuzhan_yuyong` 愈战愈勇、`jishi` 击势、`chongfeng` 冲锋、`jieduan` 截断、
  `jiatu` 假途、`fenqi` 奋起、`yangwei` 扬威、`quanjun_tuji` 全军突击、`fufu_linwei` 缚父临危

修完：物理武将对深谋远虑的贡献 0.0%。**golden 快照字节一致**（固定测试集不使用这些战法）。
教训：**新战法若写「使自身造成的（策略/物理/攻击）伤害提高」，必须带 `damageType`**，否则会污染物理队候选池。

### 3.2 状态类不叠加（L2 模型已对齐引擎）

「分兵」「连击」这类**状态**不会重复施加：同类型不同战法**先施加者生效、后施加者被拒**（引擎 `inflictStatusCore` 口径）；
且 `chance` 字段一律先过士气（`× moraleRate`）。合成用例已验证：两个 p=1 的分兵 → 只有 60；两个 p=0.5 → 320（若按叠加会得 436）。

### 3.3 前三回合最优 ≠ 整局最优

实测（吕布/貂蝉/刘备，三将各 2 槽）：前 3 回合最优解前 3 回合 **27,611**（其整局 42,068）；
整局最优解前 3 回合只有 20,069（但整局 **52,139**）。
单将整局最优会主动引入**叠层增伤**（深谋远虑 / 愈战愈勇），属正常——**看结论必须带口径**。

## 4. 实现要点与坑（改代码前先看）

- **「武将选取 / 战法选取」候选搜索（2026-09-28）**：候选太长（武将 158 / 可学战法 240+），滚动找一条很费劲
  → 面板给每个选取 select 配了搜索框（`teamConfig.ts`：`pickHtml` / `bindPickSearches` / `applyPickQuery`，
  样式在 `roundModel.css` 的 `.rm-pick*`；L2/L3/L4 三页共用）。
  - **只重建该 select 的 `<option>` 列表** —— 不发 `change`、不重渲染、不回调 `onChange`：选取逻辑与已选值完全不变；
    已选项与「（空槽 n）」始终保留在候选里（搜索绝不会让 `select.value` 变成空）。
  - 匹配 = 空白分词 **AND**、大小写不敏感。武将有 名 / 势力 / 兵种 / SP 标签 / id / **拼音首字母 + 全拼**
    （`web/data/pinyin.json`，与主站武将池搜索同口径）；战法有 名 / id / 出手位 / 品级。右侧提示「N 项匹配」/「无匹配」。
  - 搜索词按「**面板根节点 + cfg 身份**」保持：同一 cfg 重渲染（改等级 / 换将 / 改兵种）后不丢；
    **换 cfg（L4 切对手 = 换 cfg 对象）自动清零**，同页我方 / 对手两面板互不影响。Esc 清空搜索词。
    回车不做自动选中 —— 选中依旧只走原 select 的 `change` 路径。
  - 测试：`tests/team_config_search.test.ts`（9 个，jsdom：候选收窄 / 已选值不变 / 不回调 / 拼音与多词交集 /
    空槽与已选项保留 / 清空还原 / 带搜索词仍能正常选中 / 重渲染保持 / 换 cfg 清零 / 双面板隔离）。

- **引擎事件流的统计口径**（L4 全靠它）：
  - 伤害 = `attack_hit` + `damage`（归属 `creditToId ?? sourceId`，`creditToId` 是「指挥队友攻击」的归属，如奇兵拒北）+ `dot_tick`（`casterId`）+ `split_damage`；
  - 恢复 = `heal.amount`，按 `sourceId` 归属；
  - `status_inflicted` **只带 `unitId` / `statusType` / `detail`** → 控制时长从 `detail` 文本里解析（`parseDuration`：`持续 N 回合` / `持续至战斗结束`，兜底 1 回合）；
  - `dot_tick` **没有 `skillName`** → 只能按 `skillId` 映射。
- **`myIds` 必须用我方武将 id 集合**（`new Set(myTeam.map(g => g.id))`）。曾误写成 `new Set(right.map(...))`：交换场地的半数场次兵力比例反号，症状是「胜率 85.6% 却兵力优势 −13.8」。修好后不变式成立：**胜场 ⇔ 兵力比例更高**。
- 判定分支统计要用 `if/else`：`win` 与 `loss`/`draw` 不能各记一次（否则胜+负 > 场次）。
- **改文件名 / 移动文件后必须重启 vite**：旧模块图会让页面白屏。四页都已加 error boundary，回归测试断言了 tab 标签与关键 `select`。
- 首次加载要注意 `web/data/heroes.json` 是**编译期内联**的：确认起服务的是哪棵树。
