>   说明 `2` / `3` 的真正区分**不是「数值 vs 状态」**，而更可能是「**取较高** vs **先施加者生效**」：
>   `2` = 同类保留一份、取较高；`3` = 同类保留一份、先施加者生效（不分高低）。
> - 若如此，则 `2` 组里那些「多条同类应否合并」的判定不变，但**引擎对 `trigger_boost`（含生效几率）走的是「同类型取较高、跨类型逐条相加」**（`action.ts:522` 注释「多种 trigger_boost 按施加顺序逐条相加叠加」）—— 与 `3`「先施加者」不符，需用户确认哪条口径优先。

## 四、引擎对照（实测 + 代码）

### 结构性事实：引擎的冲突判定按「战法类型」分域

`src/engine/action.ts` 里两条查找都以 `sourceSkillType` 为域：

- `sameSource`（`action.ts:3526-3535`）：`s.sourceSkillType === sourceSkillType && s.sourceSkillId === sourceSkillId`
- `sameType`（`action.ts:3549-3560`）：`s.sourceSkillType === sourceSkillType && s.sourceSkillId !== sourceSkillId`

后果 = **跨战法类型（主动/指挥/被动/追击）的同名效果/同数值效果永不冲突，各自入栈**。
例外只有规避 `evasion`（入口级无差别互斥，`action.ts:3277` 起）、急救 `first_aid` 与休整 `rest`（各自专门分支）。

而包内 `replace_type` 是**逐效果**的（每个机制码一个值），数据里没有「战法类型」这一维。

### 探针实测（`scripts/_probe_conflict_class.mts`，本机真引擎）

```
— ① 混乱：指挥 → 主动（跨类型）
  状态: confusion(command:cmd_confuse) rem=2 | confusion(active:act_confuse) rem=2
  冲突事件: (无)

— ② 混乱：指挥 → 指挥（同类型）
  状态: confusion(command:cmd_c1) rem=2
  冲突事件: 混乱冲突（已有指挥战法施加的混乱），未生效

— ③ 攻击属性：+50 → +30（同类型，验证「替换」还是「取较高」）
  状态: attack_buff(passive:p_atk_big) amount=50 rem=3
  冲突事件: 攻击增益冲突，数值取较高 50

— ④ 攻击属性：+50（被动）→ +30（主动）（跨类型）
  状态: attack_buff(passive:p_atk) amount=50 rem=3 | attack_buff(active:a_atk) amount=30 rem=3
  冲突事件: (无)

— ⑤ 造成伤害提高：0.3（指挥）→ 0.2（主动）（跨类型，同分类）
  状态: damage_boost(command:cmd_boost) rate=0.3 rem=3 | damage_boost(active:act_boost) rate=0.2 rem=3
  冲突事件: (无)

— ⑥ 急救：指挥 → 被动（跨类型）
  状态: first_aid(command:cmd_heal) rem=999 | first_aid(passive:p_heal) rem=999
  冲突事件: (无)

— ⑦ 急救：指挥 → 指挥（同类型）
  状态: first_aid(command:cmd_heal1) rem=999
  冲突事件: 持续型急救冲突（已有指挥战法cmd_heal1施加的持续型急救），先施加者生效，未生效
```

### 逐组判定

| 包内分组 | 应有行为 | 引擎现状 | 判定 |
|---|---|---|---|
| **1** 任何效果都不冲突 | 不同战法的士气升降各自生效 | 士气：`action.ts:3713-3724` 两个方向都绕过冲突（2026-10-18 改，逐实例相加）✓；标记 / 子技能 / 直接伤害本就不进状态栈 ✓ | **对齐** |
| **0** 属性替换 | 新数值**替换**旧数值（不分谁高） | 同战法类型内走「取较高」：`+50` 后 `+30` 被拒并报「数值取较高 50」（probe ③）；急救走「指挥互斥、先施加者生效」（probe ⑦） | **错位** |
| **0**（跨类型） | 同上（替换） | 跨类型各自入栈并存、数值相加（probe ④） | **错位**（若「替换」不分类型） |
| **2** 效果不叠加（数值） | 同类只留一份（取较高／先到） | 同类型取较高 ✓；**跨类型各自入栈并进同一加算池累加**（probe ⑤：0.3 + 0.2 = 0.5） | **错位** |
| **3** 效果不叠加（状态） | 同名只留一个（先施加者生效），不分战法类型 | 同类型先施加者生效 ✓（probe ②）；**跨类型各挂一条**（probe ①：两条混乱，`getStatus` 只读第一条） | **错位** |

### 受影响的引擎状态（按包内分组）

- **0 类**：`attack_buff` / `defense_buff` / `strategy_buff` / `speed_buff`（含 `percent` 形态）、`attack_range_buff`、`first_aid`、`rest`、`heal_reduce`（207 不可回复兵力）、DoT `sorcery` / `burning` / `panic` / `curse` / `ignite`
- **2 类**：`damage_boost`（`caused` / `taken`）、`damage_reduce`、`heal_boost`、`trigger_boost`
- **3 类**：`confusion` / `rampage` / `cowardice` / `hesitation`、`combo`、`split`、`counter`、`evasion`、`evade_chance`、`insight` / `break_def` / `soothe`、`cover`、`taunt`、`redirectAllyPhysical`…
- **1 类**：`morale_boost`、标记类、`control_spread` 等（本就不参与冲突判定）

> 引擎的冲突实现是**按 StatusType 分派**的（不是按机制码），所以「对齐包内」要么给每个 StatusType 标注分组，要么在 `MECHANISM_DICT` 之外再建一张 `StatusType → replace_type` 表。前者改动小、后者可核对。

## 五、修复提案（三档，需用户拍板）

| 档 | 改动 | 影响面 | 验证成本 |
|---|---|---|---|
| **A（最小）** | 状态类（3）互斥提到入口、**无差别**（像规避那样），跨类型命中补 `status_conflict` 事件 | 控制/连击/分兵/反击不再跨类型叠加（probe ① 两条 → 一条） | golden 需重生成（控制覆盖率下降，可能有战报差异） |
| **B** | 数值类（2）改「同分类键跨类型取较高」，不再累加 | 增伤/减伤/发动率/恢复加成来源合并 → 伤害整体略降 | golden 重生成 + 端到端对拍（`scripts/_diag_*`） |
| **C（动静最大）** | 0 类改为「新值替换」（含急救/休整：后施加者替换数值，而不是互斥拒绝） | 属性覆盖规则反转（弱效果能盖强效果）、DoT/急救数值替换 | golden 重生成 + 全量 975 例 + 用户手感验收 |

三项都必须保留现有豁免：宝物 `treasure:` / 陈寿 `chenshou:` 来源不参与冲突（2026-10-17 报障口径）。
