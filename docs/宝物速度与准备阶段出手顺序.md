# 准备阶段「改速度的来源」与出手顺序（2026-11-06 报障落地）

## 现象

同一队内，卫瓘佩戴 +30 速宝物（锻造词条「灵动」，`TreasureLoadout.affix = { name: '灵动', value: 30 }`）：

- 「战斗开始前」的准备阶段，**吕蒙先释放一类指挥**（白衣渡江）；
- 正式回合开始后，**卫瓘先行动**。

同一场战斗出现两套出手顺序，且与面板不符：卫瓘 40 级 82 速 + 宝物 30 = 112，吕蒙 88。

## 根因（同一根因有三处）

`src/engine/combat.ts` 的准备阶段顺序曾是：

```
buildTurnOrder（读 effectiveStat('speed')）  ← 此刻没有任何宝物 / 被动加成
  → push battle_start
  → prep_phase formation / troop（二级兵种状态）
  → prep_phase treasure（applyTreasureEffects）   ← +30 速在这里才挂上          【来源 A】
  → prep_phase chenshou
  → prep_phase skill
      → 遍历 turnOrder：triggerPassiveSkills('battle_start')   ← 百战精兵 +32 速在这里才挂上  【来源 B】
      → 遍历 turnOrder：triggerCommandSkills（一类指挥）         ← 读的是旧顺序
```

正式回合每回合用 `buildPriorityOrder` 按**当前生效速度**重排，所以第 1 回合与 `battle_start.turnOrder`
（第 1 回合被 `roundOrderIds` 回填）都是"卫瓘先"，把准备阶段的顺序错误掩盖掉了——这也是用户
「实战后卫瓘先」观察的来源。

来源 B 是同一根因的另一半，且更容易撞上：`battle_start` 里给自身加速度的被动共 5 个——
百战精兵 +32（`baizhan_jingbing`）、速战兵法 +28 受谋略（`suzhan_bingfa`）、
疾风突击 / 运筹帷幄 / 速战坚守 +24（`jifeng_tuji` / `yunchou_weiwo` / `suzhan_jianshou`）。

来源 C（2026-11-06 独立复核时发现，见 `docs/复核-prep出手顺序-2026-11-06.md`）：**一类指挥自己也会改速度**——
其疾如风（`qiji_rufeng`）`initialOutput` 给我军全体 `speed_buff +41`（受谋略，成长 0.075/点），
魏武之世（`weiwu_zhishi`）`output` 给敌军全体 `speed_buff −15%`（受谋略，成长 0.045/点）。
它们的写入发生在 `triggerCommandSkills` 循环**内部**，循环顺序早已按重排二锁定 ——
这一处**不能靠"循环外再重排一次"修**（那时命令已经执行完了，顺序是既成事实），
必须**逐个重排尾部**。

## 修法

`src/engine/combat.ts`：

- 新增 `applyOrder = buildTurnOrder(...)`：**施加顺序**，与修复前逐字节一致（此时宝物 / 陈寿状态尚未挂载）。
  冲突判定「先施加者生效」依赖这条遍历顺序，所以它只用于施加（二级兵种 / 宝物 / 陈寿状态）。
- 新增 `refreshTurnOrder()`：按当前生效速度重算 `turnOrder` 并回填 `battleStartEv.turnOrder`。
  **在两个环节之后各调用一次**：
  1. 宝物 / 陈寿状态挂载完成、进入 `prep_phase: 'skill'` 之前（来源 A）；
  2. 全部 `battle_start` 被动跑完、一类指挥之前（来源 B）。
  3. **命令循环内部逐个重排**（来源 C）：每执行完一个一类指挥，就把「尚未执行」的尾部按最新速度重排，
     已执行的前缀不动。没有速度变化时重排结果完全相同，所以对普通一类指挥零副作用。

刻意的取舍：

- **不动 `prep_phase` 事件的顺序**（formation → troop → treasure → chenshou → skill），战报呈现不变；
- **不动施加顺序**，避免"先施加者生效"的冲突判定结果因这次修复被连带改变；
- `applyOrder` 与重排后的 `turnOrder` 在无宝物 / 无陈寿状态 / 无速度被动时完全相同，所以这类对局零变化
  （golden 快照未变，见下）。

## 证据

- 探针 `scripts/_probe_treasure_order.mts`（卫瓘中军 / 吕蒙大营，其余为盾木桩）：

  | 场景 | 修复前 prep 一类指挥 | 修复后 prep | 第 1 回合 |
  |---|---|---|---|
  | 裸将 | `['lvmeng','weiguan']` | `['lvmeng','weiguan']` | 吕蒙先（一致） |
  | 宝物灵动词条 +30 速 | `['lvmeng','weiguan']` ✗ | `['weiguan','lvmeng']` | 卫瓘先（一致） |
  | 被动百战精兵 +32 速 | `['lvmeng','weiguan']` ✗ | `['weiguan','lvmeng']` | 卫瓘先（一致） |
  | 其疾如风 +41（`scripts/_probe_prep_command_speed.mts`：张辽 211 / 吕蒙 100 / 卫瓘 82） | `['h27','lvmeng','weiguan']` ✗ | `['h27','weiguan','lvmeng']` | 张辽 > 卫瓘 > 吕蒙（一致） |

  `prep_phase` 顺序修复前后均为 formation → troop → treasure → skill。

- 回归 `tests/treasure_prep_order.test.ts`（5 例）：宝物 +30 速 prep 顺序卫瓘先且与第 1 回合一致 /
  battle_start 被动 +32 速同口径 / 一类指挥其疾如风 +41 逐个重排同口径 / 三个来源都不挂时吕蒙先（反例守卫）/
  `prep_phase` 顺序不变（防止用"把宝物阶段挪到 battle_start 之前"的粗暴修法换顺序）。
- `npx tsc --noEmit` 通过；`npx vitest run` 全量 **152 files / 1425 tests** 通过，**golden 快照无需重生成**
  （固定测试集既不戴速度类宝物 / 陈寿特性，也没有「一类指挥自身改速度导致跨阵营反转」的编成，
  `applyOrder` 与每次重排结果一致，事件流逐字节不变）。

## 口径（勿再询问）

1. 凡是在**准备阶段**改 `speed` 的来源（宝物特效与锻造词条、陈寿特性、二级兵种状态、battle_start 被动），
   都必须在 `refreshTurnOrder()` 之前施加；新增这类来源就要在它之后补一次重排。
   **一类指挥自身改速度**（其疾如风 / 魏武之世 这类 `phase:'prep'` 且输出含 `speed_buff` 的战法）走的是
   命令循环内的逐个重排 —— 新增同类战法不需要额外接线，但**不要**把它改成"循环外再重排一次"
   （那时顺序已成既成事实，重排只会改显示、不改执行）。
2. 战报里「战斗开始前」的出手顺序必须与第 1 回合一致；`battle_start.turnOrder` 每次重排都要回填。
3. 施加顺序（`applyOrder`）与结算顺序（`turnOrder`）是两件事，不要合并——合并会让"先施加者生效"的
   冲突判定随速度变化而漂移。
4. `prep_phase` 的事件顺序（formation → troop → treasure → chenshou → skill）不许为了让排序正确而被挪动。
