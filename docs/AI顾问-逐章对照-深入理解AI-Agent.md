## 第 1 章 · Agent 基础知识 —— ✅ 做到

**书上的主线**
- `Agent = LLM + 上下文 + 工具`，更工程的说法是 **`Agent = Model + Harness`**、**`Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正`**（正文：`book/chapter1.md` 行 11–21、263–287）。
- 五要素的定位：Context 给感知、Tools 给手脚、Constrain 故障安全默认、Verify **只看结构化数据**（不看模型自由文本，因为可能被提示注入）、Correct 先静默重试再暴露中间态（行 281–287）。
- 三条核心原则：保持简单、保持透明、设计好 ACI；以及"从简单到复杂"的编排取向（行 341–351、370–374）。

**顾问怎么做到的**

| 书里的要素 | 顾问的实现 | 证据 |
|---|---|---|
| 上下文管理 | 每轮消息编排：`SYSTEM_PROMPT → budgetHint → <advisor_box> → <advisor_prefs> → history → 本轮提问`；loop 本身**无状态**（历史和档案由页面传入） | `web/advisor/loop.ts:165-174` |
| 工具接口 | `ToolSpec { name, description, schema, cost, run }`，description 写清"何时用 / 边界 / 代价" | `web/advisor/tools.ts:677`（注册表）、`web/advisor/types.ts`（ToolSpec） |
| 约束 | ① 预算四件套：单轮 40 次调用 / 200,000 场 / 900 秒 / 1,000,000 token，**超限拒绝执行**并回灌"预计多少场、已用多少"；② 长搜索（≥2000 场）开跑前**报价 + 等用户点确认**；③ box 严格模式把配将类搜索的候选池收窄 | `web/advisor/types.ts:154,195-200`、`web/advisor/tools.ts:1639`（确认门）、`web/advisor/loop.ts:226-237`（次数超限收口） |
| 验证 | **关 1 合法性**（`validateAdvisorPlan`：存在 / 可学 / 每将 ≤2 槽 / 全队唯一 / 互斥 / box）→ **关 2 数字溯源**（回答里的 `{value, evidenceId}` 回 trace 核对，容差 `max(0.5% × \|actual\|, 1)`）→ **关 3 独立复算**（固定种子 `20260929` × 20 场，标准木桩，不采信 AI 那次搜索的数字） | `web/advisor/gate.ts:128`、`231`、`250`、`194-196`、`267-303`、`374` |
| 纠正 | 工具抛错**带 code / 带字段名**回灌让模型自纠（"plan.slots[1].skillIds 必须是字符串数组…"）；厂商不支持工具调用 → 去掉 tools 降级重试并**如实标注**；取消信号在每次请求/工具前检查；token 超限后"不再执行工具，但让模型把话说完" | `web/advisor/tools.ts:523-556`、`web/advisor/loop.ts:196-205`、`128-134`、`210-216` |
| Verify 只看结构化数据 | 关 2 / 关 3 只读 trace 里工具的 `data`，**完全不参与 LLM 的措辞**；方案卡数字由渲染层直读 `tool.data` | `web/advisor/gate.ts:231-256`、设计文档 §5「关 3 防自己验自己」 |
| 保持简单 / 透明 | 五个模块各一职责、三层互不认识（传输层不认识配将、工具层不认识 LLM、循环层不认识 DOM）；界面上工具调用压成**一行轨迹** + 证据清单 + 成本行 | `docs/AI配将顾问-设计.md` §2、§13②；`web/advisor/trace.ts` |
| 编排取向（从简单开始） | 单 Agent 自主循环 + 确定性工具，没上多 Agent / 复杂框架 | `web/advisor/loop.ts:185-272` |

**判定**：✅ **做到**。这是全书对顾问最"对症"的一章——顾问几乎可以当成第 1 章 Harness 五要素的一份实例答案，而且其中"验证只看结构化数据"这条书里点名的原则，顾问是**用代码强制的**（gate 读 trace，不读模型的话）。

**这一章里没做到的两处（记录，不是建议）**
- **模型选型**：书里说"不要只看排行榜，要在你自己的任务上评估"（行 359）。顾问把模型做成可配置（baseURL / model / key，默认 `deepseek-chat`），跑分脚本也写好了，但**仓库里还没有留下任何一份记分卡**（`docs/顾问评测记分卡-*.md` 不存在）。
- **护栏与安全性**（行 456 起）里的"上下文层来源标记 / 执行层审批"：顾问只有"box 外将法禁用应用"这一道审批，没有对外部内容（截图文本、检索结果）加"这是资料不是命令"的来源标记。

## 第 2 章 · 上下文工程 —— ✅ 做到（两处细节有偏差）

**书上的主线**
- 先讲清 API 的上下文结构：消息角色（system / user / assistant / tool）、带工具调用的多轮循环（`book/chapter2.md` 行 41–260、372–504）。
- **KV Cache / Prompt Cache 是架构约束**：系统提示词定下来就别改；**动态元素放到缓存边界之后**；工具定义顺序固定；别用滑动窗口丢工具结果（行 528–574，尤其是"常见的错误上下文管理模式"）。
- 提示工程四件事：人格 / 格式 / **流程驱动而非规则堆砌** / 业务规则细化；工具定义也是上下文的一部分（行 596–736）。
- 上下文压缩：什么时候压、怎么压、与缓存的矛盾（行 962–1066），以及"隔离优于压缩"（子 Agent，行 1058）。

**顾问怎么做到的**

| 书里的主张 | 顾问的实现 | 证据 |
|---|---|---|
| 标准消息结构 + 工具调用循环 | OpenAI 兼容传输：SSE 流式解析、`tool_calls` 分片拼装、`assistant(toolCalls) → tool(result)` 回灌 | `web/advisor/transport.ts:30-55`、`web/advisor/loop.ts:223-267` |
| 工具定义顺序必须固定（缓存友好） | 每轮 `createTools()` 按**固定注册顺序**生成 specs，从不满天排序 | `web/advisor/loop.ts:176`、`web/advisor/tools.ts:677` |
| 大块内容别进上下文 | `summary`（≤200 字）+ `brief`（≤15 行）进模型上下文，几万行跑批明细只走 `data`（挂 trace 给渲染层直读） | `web/advisor/tools.ts:7-10`、设计文档 §3 |
| 流程驱动的系统提示词 | 系统提示词 = **7 条硬规则** + 每个工具"何时用" + "比较两个战法 / 给我配将"两套**标准做法**；预算数字不由提示词写死，而是 `budgetHint()` 从 `BudgetState` 生成 | `web/advisor/loop.ts:29-75`、`77-84` |
| 业务规则细化 & 边界声明 | 硬规则里写死：排序口径 = 综合胜率、区间重叠必须说"分不出来"、木桩边界（控制/防御型队友量不出来）、工具报错不许编结果 | `web/advisor/loop.ts:31-47` |
| 隔离优于压缩 | 明细不进上下文即"隔离"；历史用**紧凑转录**（`historyFrom`，上限 `REPLAY_TURNS=6` / `REPLAY_MAX_CHARS=12000`）；会话超 30 轮丢最旧 + 1.5MB 裁剪 | `web/advisor/memory.ts:50-53,326` |

**两处与书不一致的细节（真实偏差，值得知道）**
1. **动态注入块的位置**：书里明说"把时间信息作为用户消息追加到对话**末尾**""所有动态元素放到缓存边界**之后**"（行 546、568）。顾问把每轮都可能变的 `<advisor_prefs>`（以及用户一改就变的 `<advisor_box>`）作为 **system 块摆在 history 之前**（`loop.ts:165-174`）。顾问自己给了理由——"档案是这个人一贯要什么，先给身份约束再给经过"（`loop.ts:101-105`）——语义上说得通，代价是**每轮从档案块起的前缀缓存都可能失效**（好在 history 本身每轮增长，本来也要重算后面那段）。
2. **没有 Skill 形态**：第 2 章"动态提示词与 Agent Skills"讲的是"能力按需加载，别一次性塞满系统提示词"（行 736–828）。顾问的选择是把能力全部做成 **19 个专用工具 + 一个长系统提示词**，按需加载只体现在 `list_skills` 分页与 box 超长截断提示 `get_my_box`。这不是错，但它把"上下文成本"这一侧的压力交给了工具描述（书第 4 章马上要讲这个代价）。

**判定**：✅ **做到**。第 2 章的技术栈（角色结构、工具循环、缓存友好的静态前缀、压缩与隔离）顾问都有对应实现；上面两处属于"选了另一条合法路线"，其中第 1 条是**唯一一条我认为书上会直接批评**的地方。

## 第 3 章 · 用户记忆和知识库 —— 🟡 部分做到

**书上的主线**
- 用户记忆的提取要同时满足**选择性 / 抽象化 / 结构化**三条规则（`book/chapter3.md` 行 15–41）。
- 记忆分两层：**轨迹**（单会话、append-only 的流水账）与**用户长期记忆**（跨会话、会被反复改写淘汰的档案）（行 72–86）。
- 四种存储格式从 Simple Notes 到 Advanced JSON Cards，选择标准是"关键且少量 → 结构化卡片；大量非关键 → 简单事实"（行 88–105）。
- 评估用**三层次框架**：基础回忆 / 多会话检索 / 主动服务（行 43–70）。
- 知识侧两条硬道理：**智能体化 RAG**——把检索做成 Agent 调用的工具、多轮迭代而非一次性管道（行 542–556）；检索内容要当**不可信输入**（间接提示注入，行 556）。

**顾问怎么做到的**

| 书里的主张 | 顾问的实现 | 证据 |
|---|---|---|
| 轨迹层（append-only） | `dsh-advisor-session-v1`：每轮存"用户 + 回答 + 证据清单（**不存 `data`**）+ 方案三关结论"，按 `turn.id` **幂等**追加；中断/关页面落 `partial` 轮（不编不补） | `web/advisor/memory.ts:38,152-154,252-273`；设计文档 §14.2 |
| 长期记忆层（会被改写/淘汰） | `dsh-advisor-profile-v1`：轮末一次**非流式小请求**（temperature 0、不带 tools）抽 `{"add":[…],"remove":[…]}`；同"标签+取值"→ `seen+1`（当置信度），超 24 条淘汰最久未确认的 | `web/advisor/prefs.ts:36,107-140`、`web/advisor/memory.ts:440-491` |
| 提取三规则 | 选择性/抽象化/结构化由抽取提示词承担（只抽"对未来有用"的偏好，写成 `{key,value}`） | `web/advisor/prefs.ts:36-55` |

| 检索内容当不可信输入 | box 那条纪律是同一个思想：**截图识别只让模型抄名字，id/阵营/兵种一律以库为准**，对不上一律进"待确认"不静默采纳 | 设计文档 §15.1 |

| 缺口 | 书里怎么要求 | 顾问现状 |

## 第 4 章 · 工具 —— ✅ 做到（形态只走了一半）

**书上的主线**
- 能力表达是一条从**专用工具**到 **Skill + 通用执行器**的谱系；默认取向"通用优于专用"，但四种情况该退回专用工具：安全/权限/审计、屏蔽平台差异、高频、**参数结构复杂**（`book/chapter4.md` 行 38–68）。
- 粒度**偏向整合**：多个同构工具应合成一个（`read_document(file_type=…)`），因为整合降低选择负担（行 51）。
- **工具描述的艺术**：说"什么时候用"而不是"能做什么"；**边界比能力更重要**；参数给具体例子；耗时工具要标注代价；给 1–5 个真实调用示例（行 70–86）。
- **参数传递保真性**：不许静默转换/静默注入（Cursor 弯引号案例），"模型感知到的世界与工具操作的世界之间不能有系统性偏差"（行 88–98）。
- 生态（MCP / Skill Hub）与分层披露（工具太多怎么办、主动工具发现）（行 100–217）。

**顾问怎么做到的**

| 书里的主张 | 顾问的实现 | 证据 |
|---|---|---|
| 参数复杂 / 高频 / 需审计 → 做成专用工具 | 19 个结构化工具；把 L2/L3 的**千~万场搜索**包成 `optimize_skills` / `optimize_mates` / `optimize_both`（参数多、耗时长、要计费，正是"该退回专用工具"的典型） | `web/advisor/tools.ts:900,989,1081` |
| 粒度偏向整合 | **被实跑逼出来的整合**：模型曾 28 次调用逐个查战法 + 9 次手搓 `simulate` 对拍 → 于是加了 `simulate_many`（一次对拍 ≤8 套）和 `optimize_both`（搜队友 ↔ 搜战法交替，一次给完整方案），把 9 次压成 1 次 | 设计文档 §13 补丁 2、§13 切片四①；`web/advisor/tools.ts:809,1081` |
| 描述"什么时候用" + 边界 | 系统提示词按**用途分组**列工具（对手池 / 胜率 / 木桩 / 我的 box 与信息），并写明首选（"最强/怎么配"默认 `optimize_winrate`；只有用户明确要木桩才用伤害工具） | `web/advisor/loop.ts:54-69` |
| 标注执行代价 | 每个工具带 `cost`，长搜索先**报价**（"预计 8,062 场 / 约 48 秒"）再跑；拒绝则**额度原路退回**并告知"不要重试同样规模" | `web/advisor/types.ts:154-156`、`web/advisor/tools.ts:1639` |
| 边界说明（做不到什么） | `hero_detail` 对下架武将成为显式告警：**offlineReason + "模拟数值会系统性偏低，只能看方向"**；`optimize_mates` 主动声明"防御/控制型队友的价值量不出来" | 设计文档 §13 补丁 2、切片三；`web/advisor/tools.ts`（hero_detail 分支） |
| 参数保真、不许静默修正 | `assertPlanShape` **逐字段点名报错**（"plan.slots[0].heroId 缺失：不确定就先 search_hero"），坏输入不静默改写成另一个 plan | `web/advisor/tools.ts:523-556` |
| 第三方能力安全 | 没有第三方工具，所有工具都是同仓库代码 → 书里 MCP/Skill Hub 的供应链风险面**天然不存在** | — |

**只做到一半的地方**
- **Skill 谱系完全没有**：书里说"快变的能力用 Skill 维护成本远低于专用工具"（行 63）。顾问的一切能力都是代码工具，改一点就要发版。本项目是纯前端单机应用，这条的收益有限，但**"数据表/口径说明"这类内容**（比如战法机制解释）其实已经半只脚在 Skill 的地盘上——现在它们硬编码在 `skill_detail` 的返回值里。
- **分层披露 / 主动工具发现** 🟡：书里给了"目录 + 按需加载""工具搜索"两条路（行 133–217）。顾问用的是第三种：**全量 19 个工具常驻 + 系统提示词分组**。19 个还撑得住，再长就会顶到书里说的"选择负担"。
- **通用执行器（code_interpreter）** ⬜：本项目无沙盒，且纪律上明确**不让模型算数**，所以这是有意不做。

**判定**：✅ **做到**。"描述的艺术""粒度整合""参数保真"三条都落实了，而且**证据是实跑教训驱动的**（不是照着最佳实践抄的）。缺的那半条谱系（Skill）对本项目价值有限。

## 第 5 章 · Coding Agent 与通用 Agent —— ✅ 原则做到（场景不同）

**书上的主线**
- Coding Agent 之所以成熟，不是因为模型强，而是因为软件工程几十年的基础设施天然是 Harness：**验收基线 / 执行边界 / 反馈信号 / 回退手段**（`book/chapter5.md` 行 127–149）。
- 四条可迁移原则：**约束优先于指导**（能用代码强制就别写文档）、**验证要自动化**、**反馈越快越结构化越好**、**回退要可靠**（行 159–166）。
- 故障分类学：API 层 / 工具层（含"反复返回同一个错，模型不加改变地反复重试"）/ 上下文层 / 控制流层（死循环、死亡螺旋）（行 172–186）。
- "代码作为业务规则的约束 / 系统适配器 / 元能力"（行 366–600）。

**顾问怎么做到的**

| 书里的原则 | 顾问的实现 | 证据 |
|---|---|---|
| 约束优先于指导 | 预算、box 收窄、关 1 合法性都是**代码强制**；系统提示词只写"该怎么用"，从不承担"必须执行"的职责 | `web/advisor/types.ts:195-200`、`gate.ts:128`、`tools.ts:273-328` |
| 验证自动化 | 关 1/关 2/关 3 全自动，无需人看；关 3 用**固定种子 + 20 场**标准口径独立复算，堵住"AI 挑种子 / 调小场次造优势" | `web/advisor/gate.ts:267-303` |
| 反馈越结构化越好 | 工具错误带 `code` 与字段名回灌；书里点名的反面（模型盲试同一个错 4 次）在本项目**真实发生过**，修法是改报错文案而不仅是重试 | `web/advisor/tools.ts:523-556`；设计文档 §13 补丁 2 |
| 回退要可靠 | 取消（AbortSignal）立即停；报价被拒不跑且额度退回；跑批缓存命中不重跑；中断落 `partial` 轮；`pagehide` 兜底 | `web/advisor/loop.ts:128-134`、`tools.ts:1639`、`cache.ts`、设计文档 §14.2 |
| 故障分层治理 | API 层：`auth / cors / network / format` 分类给可操作提示；工具层：报错回灌 + 自纠；控制流层：次数/token 上限后强制收口（"基于已有结果作答"）；上下文层：无工具降级 | `web/advisor/transport.ts:64`、`loop.ts:196-216,226-237` |
| 代码承担确定性计算 | 纪律"**AI 不下场算数**"：数字只来自引擎与跑批，方案卡数字由渲染层直读 `tool.data` | 设计文档 §0、§5 关 3① |
| 四象限（目标清晰度 × 验证自动化） | 顾问把"配将"这个模糊任务**改造成可自动验证的任务**：目标 = 胜率/期望，验证 = 引擎复算——这正是书里说的"Harness 的目标是把任务推向'目标明确 + 验证自动化'象限" | 设计文档 §1、§5 |

**没做到的一处（书里明确点名的第 4 类工具故障）**
- **没有"同一错误反复重试"的熔断器**：书里说这是工具层最危险的一种（行 181），还专门提到 Claude Code 的 Circuit Breaker。顾问目前只有"总次数上限"这一层粗保险；实跑里模型 4 次盲试同一个 `simulate` 错误，是靠**改报错文案**治好的，不是靠熔断。

**判定**：✅ **原则做到**。如果按第 5 章的表 5-1，顾问所在的象限是"目标明确 + 结果可自动验证"——这就是为什么它能做得比一般聊天式助手可靠：**它把赛道选在了 Harness 工程最吃得开的地方**。

**没闭环的那一层**
- **真模型跑分没留档**：`scripts/advisor_eval.mts`（`ADVISOR_KEY=... npx tsx` → `docs/顾问评测记分卡-<时间戳>.md`）已经就绪，但仓库里**一份记分卡都没有**（`docs/顾问评测记分卡-*` 无匹配）。也就是说：**"改提示词后是变好还是变吵了"这个问题，目前还没有历史数据可查**。

**判定**：✅ **做到**。第 7 章是顾问**第二强**的一章：它把书里最容易被忽略的两条（"坏模型要被抓住"、"回答里的数字必须可溯源"）都做成了自动判分。差的只是"跑分留档 + 评估集统计"这一层仪式。

## 第 9 章 · Agent 的持续进化 —— ✅ 做到（不含参数侧）

**书上的主线**
- **起点不是"总结"而是"评价"**：不知道任务是否完成、哪一步造成成败，反思只是猜测；错误的评价一旦进入长期知识/提示词/训练数据，影响会跨任务放大（`book/chapter9.md` 行 19–23）。
- **三层验证结构**：结果验证器（读测试/工具返回，答"是否真的办成"）→ 过程验证器（规则/权限/动作序列）→ 质量验证器（Rubric 评价表达），**越靠下越依赖代码和环境真值**（行 25–31）。
- **四种更新方式**：经验知识库 / Prompt 与 Skill / 程序与 Harness / 模型参数，各有边界（行 52–69）；"路由结果只是更新提案，尚未获得发布资格"（行 69）。

**顾问怎么做到的**

## 第 10 章 · 多 Agent 协作 —— ⬜ 未做（在本项目的判据下不该做）

**书上的主线**
- **唯一判据**：协作过程是否引入了**单个 Agent 在生成时无法获得的新信息**？同一模型自我审查（无效）、不同 Agent 辩论（持平）、**审核者使用测试执行结果 / 视觉反馈 / 外部工具验证（显著提升）**（`book/chapter10.md` 行 46–67）。
- 步骤预算与预算意识：单纯加步骤不提升性能，Agent 需要显式预算感知（行 73–75）；多 Agent 的成本必须被收益覆盖（行 77）。
- 共享上下文的角色转换：**替换 system prompt** vs **加载 Skill** 是两种成本模型（前者破坏前缀缓存，后者保住静态前缀）（行 79–101）。
- 多 Agent 的失败模式（行 509–566）。

**顾问的现状**

| 书里的模式 | 顾问 | 说明 |
|---|---|---|
| 多 Agent 协作（辩论 / 编排者-子 Agent / 消息总线） | ⬜ 无 | 单 Agent + 确定性工具链 |
| "审核者用外部工具验证"（表 10-1 里**显著提升**的那一行） | ✅ **有等价物，而且更硬** | 顾问的审核者是**确定性复算**（关 3）与**结构化数字核对**（关 2），不是另一个 LLM。书里判据（引入新信息）成立：复算引入的是环境真值 |
| 预算意识（Budget-Aware） | ✅ 有 | 预算四件套 + 报价门 + 超额拒绝时回灌账目（"本次预计 8062 场；本轮已用 X/200000 场、Y/40 次"）正是书里说的"显式预算感知"；提示词里还专门写"额度是给你用的，不是给你省的" | 
| 角色转换的成本模型（system prompt vs Skill） | 🟡 选了 Skill 那一侧 | 系统提示词固定，每轮只**追加** box/prefs 块——保住了静态前缀（但见第 2 章那处位置偏差） |
| 多 Agent 失败模式治理 | ⬜ 不需要 | 没有多 Agent |

**判定**：⬜ **未做，且当前不该做**。顾问真正需要的外部反馈（引擎跑批、独立复算、统计区间）**用确定性代码就能拿到**，比派一个 LLM 子 Agent 更便宜也更可信——这恰好落在书里"用一个 Agent 就够"的那一侧。只有当出现"开放搜索空间、需要多路探索"的任务（例如自动挖掘冷门战法组合并互审）时，第 10 章的判据才会翻过来。

## 横向结论

### 一、顾问最"贴书"的五个地方

1. **Harness 五要素齐全且有代码强制**（第 1 章）：约束/验证/纠正在顾问里不是文档，是可测试的函数（`gate.ts` / 预算 / 报价门）。
2. **"验证只看结构化数据"**（第 1 章表格）：关 2 / 关 3 读 trace，不读模型措辞——这是防提示注入与防"自证"的同一招。
3. **工具粒度整合是被实跑逼出来的**（第 4 章）：`simulate_many`、`optimize_both`、把 L2/L3 提为一等工具——设计文档里那句"AI 就该调 L2/L3，不该自己一个个翻战法"就是书里"粒度过细增加选择负担"的实战版。
4. **智能体化 RAG**（第 3 章）：检索是工具、多轮换词、0 命中给提示——不是一次性检索管道。
5. **先评价、再叙述**（第 9 章）：数字路径与语言路径物理分离，"AI 不下场算数"这条纪律撑起了前面所有可靠性。

### 二、真正的差距（按"书里会点名"的程度排序）

| # | 差距 | 出处 | 现状 |
|---|------|------|------|
| 1 | 动态注入块（`<advisor_box>` / `<advisor_prefs>`）摆在历史之前 | 第 2 章 §缓存作为架构约束 | 每轮前缀缓存可能从该处失效；书里建议动态元素放缓存边界之后、越靠后越好 |
| 2 | 没有"同一错误反复重试"的熔断 | 第 5 章 §故障分类学（工具层最危险项） | 只有总次数上限；实跑已出现过 4 次盲试，靠改文案治的 |
| 3 | 真模型评测记分卡一份都没留 | 第 7 章 §评估驱动的模型选型 / §从报告到改进 | 脚本就绪（`scripts/advisor_eval.mts`），缺历史数据 |
| 4 | 评估集自身没有配对分析 / 多种子 / 置信区间 | 第 7 章 §统计显著性 | 10 条用例单次跑分，只够筛方向 |
| 5 | 记忆没有专项评测（三层次框架） | 第 3 章 §记忆能力的评估 | 只有 smoke（刷新续上、档案注入、新会话清对话留档案） |
| 6 | 没有"从轨迹归纳的经验知识库" | 第 9 章 §将经验沉淀为知识 | 经验目前写在提示词与设计文档里，没有独立、可检索、带验证时间的 Markdown |
| 7 | Skill 形态与 MCP 都没有 | 第 2 章 §动态提示词与 Skills、第 4 章 §工具生态 | 本项目自用、无分发需求；收益有限 |
| 8 | 异步事件驱动基本未做 | 第 6 章 §异步与事件驱动 | 只有流式 / 取消 / 报价确认；顾问不会自己找事做 |
| 9 | 后端侧可观测性/成本核算缺失（本机自用无服务端） | 第 7 章 §可观测性 | 无 span 树、无 token 成本聚合（只有本轮成本行） |

### 三、一句话总评

> 顾问不是在"用 Agent 框架搭了个聊天机器人"，而是**照第 1 章的 Harness 公式、第 2 章的上下文纪律、第 4 章的工具设计、第 7 章的评估口径，把一个模糊任务（配将）改造成了目标明确、结果可自动验证的任务**——它落在书里"最佳区域"那个象限里。它没做的三章（第 6 章异步、第 8 章后训练、第 10 章多 Agent）恰好都是**本项目形态下收益最低或不该做**的部分。真正值得补的是**第 7 章的评估仪式**（跑分留档 + 评估集统计）与**第 2 章那处缓存位置**，其次是第 5 章的熔断。
