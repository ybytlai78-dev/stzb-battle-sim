# 武将画像与皮肤外观：解包可达性取证（2026-11-07）

> 目标：回答「解包内容能不能解码出所有武将的最新画像？及其外观画像？」
> 数据来源：客户端 9.2.2 `base.apk`（2.0 GB，14 个 `assets/*.npk`）+ 热更表 `hot_20261104`；资源全量索引 `rea_stzb/index/_index_dec.txt`（115,229 条）与 `pkg/9.2.2/apk933_index_paths.json`。

## 一、三句话结论

1. **默认画像（立绘/卡面）能全量解**：1002 张，全部成功，470×592，无水印。
2. **武将「皮肤 / 外观」不是静态图，是视频**：`res/card/card_2d_videos/facade_videos/<heroid>_<n>.mp4` + 同名 `.nbs`（alpha 遮罩），207 个武将 × 2 套 = **412 套**；静态图片族里查不到任何皮肤图。
3. **这些视频不在包里**：索引第 4 字段 `0` = 未随客户端分发，需按需下载（`card_2d_videos` 全部 2788 条均为 0）。所以「皮肤外观」的**清单能全量给出，图像本体要靠游戏缓存或热更 CDN 获取**。

## 三、能解的：默认画像（卡面）

- 管线：`base.apk → assets/card_c.npk`（`NXPK` 魔数 + u32 文件数 3226 + 3226 个 zstd 帧）→ `unpacked/card_c/*.bin`（全是 KTX 容器，ASTC 4×4）→ `tools/decode_ui_astc.py` 剥 payload → `astcenc-avx2 -dl` 出 PNG。
- 实测：**total 1002 / ok 1002 / fail 0**，输出 `_all_cards_out/`（422 MB）。尺寸 470×592 共 991 张、350×480 共 10 张（老资源）、470×593 共 1 张。
- 视觉复核：`card_100003.png` 为完整立绘、无水印（官方 CDN 走 `data/watermark/` 目录，因此解包版更干净）。
- 覆盖：`card_images` 索引 1042 条，本地 `card_c.npk` 实有 1002 条；差集 40 个 id = `100778、100816–100841、111062–111091`，均在本机未打包的新版本武将。

## 八、A 路（GL 纹理 hook）验证结论：失败（2026-11-07 20:30）

**目标**：不碰 .nbs 解码，直接 hook 游戏的 GL 纹理上传，从 `glTexSubImage2D` / `glCompressedTexImage2D` 把皮肤视频的帧截下来。

**做法**：frida 17.26.1 x86_64 注入游戏进程（pid 2055，`/system/bin/app_process64`）；hook 六个可能的上传入口，统计 5 秒一次；同一会话里用 `eglQuerySurface` + `glReadPixels` 成帧（用于确认画面）。

**实测（135 秒窗口，覆盖用户完整播放一套吕蒙皮肤的全程）**：

| 指标 | 数值 |
|---|---|
| `eglSwapBuffers` | 11,783 次（持续渲染） |
| `glBindTexture` | **4,869,812** 次 |
| `glTexImage2D` / `glTexSubImage2D` | **0 / 0** |
| `glCompressedTexImage2D` / `glCompressedTexSubImage2D` | **0 / 0** |
| `glTexStorage2D` | **0** |
| `glEGLImageTargetTexture2DOES` | **0** |
| `glBindTexture(GL_TEXTURE_EXTERNAL_OES)` | **0** |

**根因**：进程内是**两套 GL 栈**并行 —— x86_64 的 `libGLESv2.so`（106,496 B 的 shim，我们 hook 的就是它）与 arm64 侧的 GLES 包装/驱动（`libGLESv2_enc_ext.so` 385,024 B、`libGLESv2_kona.so` 143,360 B、`GLESv2_kona.so`）。
游戏本体是 **arm64**（APK 只有 `lib/arm64-v8a`），经 houdini 转译后调用 arm64 的 GLES 包装，**不经过 x86_64 的导出点**；而 `Process.enumerateModules()` 在 frida 里**枚举不到任何 arm64 模块**（返回空），也就无法对其下断。
这就解释了“`eglSwapBuffers` 能 hook、`glReadPixels` 能拿到真实画面，但纹理上传全 0”——swap 与读回走的是 x86_64 EGL/GL 表，纹理路径不是。

**能拿到的**：`glReadPixels` + `eglQuerySurface` 可稳定取到 1920×1080 的成帧画面（已目视确认：主城地图、部队/武将页均正常）。
但这等价于**截屏/录屏（B 路）**，需要逐皮肤人工播放 + 无 alpha、带背景，用户已明确排除。

**结论**：按用户口径（“先探A，失败就不考虑了，已经解码的默认画像就够用了，不走B”）——**A 路到此终止**，皮肤外观图不纳入交付；已交付的是 1002 张默认卡面（470×592，无水印）。
若后续仍要皮肤图，唯一现实路径是**真机/arm64 环境**（hoodini 之外的 arm64 root 设备可直接跑原生解码器），或官方日后上架静态皮肤图。
