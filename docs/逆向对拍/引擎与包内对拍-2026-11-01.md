## 二、对齐口径

引擎没有官方 `heroid` / `skill_id` 字段，只能间接 join。

**武将**（`scripts/rag/diff.mts` 的 `alignHeroes`）：

1. 首选「引擎 id 与包内 heroid 同号」直配（`h102016` ↔ `102016`），要求名字 / 主战法 / 四维至少一项旁证成立；
2. 否则按**数值指纹**（四维初始 + 四维成长，×100 取整后拼接）取候选集；
3. 候选集内按「主战法名 → 武将名 → heroid 升序」定序，重复段 `13xxxx` 降权。

第 1 步不可省：包内同一武将有多个版本共用同一套面板 —— 普通版 `100xxx`、SP 版 `102xxx`、重复段 `130xxx`/`132xxx`。
例：赵云四条同指纹记录 `100021`(银龙冲阵) / `102001`(银龙孤胆) / `130021` / `132001`，
只取最小 heroid 会把 SP 版错配成普通版；SP 孙尚香（`102015` 蜀）错配 `100036`（吴）会假报一条势力差异。

**战法**（`alignSkill`）：按名取候选，依次用「战法类型 → 攻击距离 → 发动率」收敛；仍多条时取 `skill_id` 最小并标 ambiguous。
416 条引擎战法里 199 条在同名多候选上收敛过一次（例：「持节镇西」包内 7 条）。

**两处口径归一**（均有样本证据）：

- **追击战法没有独立攻击距离**：跟随普攻，引擎用 `range: 0`，包内用 `hit_range: 6` 作哨兵 ⇒ pursuit 不比距离。引擎 `range=0` 的 24 条里 23 条是追击。
- **发动率 ≥100 一律视为「必定发动」**：包内 100 = 无发动率概念（被动/指挥），120 = 必定发动（巾帼战阵 `200070` init=max=120、烈火焚舟 `200251`=120），引擎对应写 `triggerRate: 1` ⇒ 两侧都按 `min(100, v)` 归一。

## 三、比对字段

- 武将 13 项：四维初始 / 四维成长 / 统率 / 势力 / 兵种 / 攻击距离 / 星级 / 主战法（按名比）
- 战法 3 项：战法类型 / 攻击距离 / 发动率

### 4.5.4 造成 / 受到伤害的增减（531-534 造成侧、521 / 523 受击侧）

上一轮只映射了 `522 / 524`（受到攻击 / 策略伤害**降低**），增伤那一半一直没进对拍。
按机制码补上六条 —— 判据同样靠引擎已实现的数据反向自证，**25 个增减伤段逐条命中**（含 1 条哨兵）：

| 机制码 | 语义 | 引擎字段 | 换算 |
|--------|------|----------|------|
| 531 | 攻击伤害提高 | `damage_boost{direction:'caused', damageType:'physical'}` 正值 | `rate = (c+0.4i)/100` |
| 532 | 攻击伤害降低 | 同上，负值（常带 `attackOnly`） | 取负 |
| 533 | 策略攻击伤害提高 | `{caused, strategy}` 正值 | 同 531 |
| 534 | 策略攻击伤害降低 | `{caused, strategy}` 负值 | 取负 |
| 521 | 受到攻击伤害提高 | `damage_boost{damageType:'physical'}`（`direction` 缺省即 `taken`） | 同 531 |
| 523 | 受到策略攻击伤害提高 | `{damageType:'strategy'}` | 同 531 |

**三键定位**：`direction`（缺省 `'taken'`，见 `src/engine/action.ts:3898`）、`damageType`（缺省两类都吃）、

`HUGE_MODIFIER_RATE` 是唯一真源，测试里断言 522/524 = +10、532/534 = −10、521/523 不设哨兵）。

覆盖：可判 **228 → 263 条（50.0% → 57.7%）**，一致 113 → 142，**差异仍为 0**。

### 4.5.5 `value_type` 字段与「98 / 99 为什么映射不了」

`tb_cfg_skill_effect` 有一条 `value_type`（分布 `0: 45 / 1: 151 / 2: 10`），此前一直没用上：

- `value_type = 2` 恰好是十个属性增减码（101-105 提高 / 201-205 降低）——「属性类」的确定性判据；
- `value_type = 1` 是百分比类（伤害率、减伤、增减伤、急救、受兵种伤害）；
- `value_type = 0` 是杂类，**不等于「无参数」**：`106 攻击距离提高` 127 条槽位全带参数（`c=2` 即距离 +2）、
  `77 标记` 106 条里 46 条带的是标记 id、`151 触发效果` 36 条带的是效果 id。

⚠️ 它不能替代 `render.mts` 里的量级判据：属性类内部还分「点数」与「全属性百分比」两种编码
（`101` 的 1000/3000 与 `201` 的 11,400,000/9,000,000 都是 `value_type = 2`），只能靠 `|c| ≥ 10⁵` 区分。
同理，`522` 与 `531` 同为 `value_type = 1`，但前者的值域要 ÷100 才是百分点、后者本身就是百分点 —— **同码不同量级只能逐码定**。

**`98 / 99`（受兵种伤害 ±，共 2,565 条槽位）无法映射**：引擎的 `troopTypes` 是**目标过滤**
（`只对这些兵种的目标结算`，见 `src/engine/types.ts:256/493/692`），而 98/99 说的是
「受到**某兵种造成**的伤害 ±X%」—— 是**伤害来源**维度。`damage_reduce` / `damage_boost` 上都没有
「按来源兵种」的过滤字段（有的是 `damageSource: 'basic' | 'skill'`、`skillTypes`、`damageType`、`dotTypes`）。
结论：这批只能报「引擎未建模」，映射不进对拍。要覆盖它，得先给引擎加维度，那是功能开发不是对拍。
- **引擎无对应输出 6 条**：`白衣渡江` 20064823（302，包内 215%）、`火势风威` 20069402（305，221%）、
  `帝临回光` 20060715（304，69%）、`巧音唤蝶` 20088413（401，161%）、`黄天当立` 20000802（401，60%）、
  `名士在野` 20067802（522，22%）。这些是**引擎把效果挂在别的结构上**（子战法 / conditional 分支 / 未建模），
  不等于引擎缺失，需逐条人工确认。

**将门虎女的一个硬事实**：包内该战法只有 3 条槽位 —— 20009401 伤害率 190%、20009402 动摇 35%（`available_round=1`）、
20009403 `effect 207 不可回复兵力`。**后段的「80% 几率 / 60% 动摇」在 detail 表里根本不存在**。
引擎按官方文案写了 190→200、动摇 60%，其依据是 `web/data/skill_desc.json` 的满级文案而非 detail 槽位。
⇒ 这类战法的数值**只能以官方文案为准，detail 表不是唯一真源**。

### 属性增减类扩映射（101-104 提高 / 201-204 降低）

最高频的一类未映射码就是属性增减（101 攻击提高 1,011 条、103 谋略 762、102 防御 694、104 速度 665 …），
但**同一机制码下包内存在两种编码**，包内又没有 unit / value_type 字段可区分：

- **点数**：算无遗策「攻击与谋略 −22」→ `c=1000 / i=3000`；坚守突击「攻击、防御 +24」→ `c=2400 / i=0`
- **百分比**：魏武之世「四维 −15%」→ `c=11,400,000 / i=9,000,000`；破胆「攻击 −30%」→ `c=30,000,000 / i=0`

判据只能靠**引擎侧已实现的数值反证**。`scripts/_probe_statpoint.mts` 做这件事：取引擎里挂了
`attack_buff / defense_buff / strategy_buff / speed_buff` 的战法，按名唯一对齐到包内，把同一槽位按三条路径换算，
看哪条与引擎 `amount` 吻合。结果（33 个可判样本）：

| 路径 | 公式 | 命中 |
|------|------|------|
| 点数 | 值 `(c+0.4i)/100`、成长 `i/20000` | **31/33（93.9%）** |
| 单属性百分比 | 值 `(c+0.4i)/10⁶`、成长 `i/(2×10⁸)` | **2/33（6.1%）** |
| 百分点（误判口径） | 值 `(c+0.4i)/10⁴` | 0/33 |

合计 **33/33 —— 判据成立**，且两条路径的**量级判据**与 `render.mts` 的 `convertDetail` 现有分域完全一致
（`|c| ≥ 10⁵` 走百分比、否则走点数）⇒ 扩映射只需处理**符号**：201-204 是「降低」，引擎 `amount` 为负，
故包内正值 × (−1)；提高类 × 1；成长率两侧恒为正，不翻号。

**三处容易踩的坑，都写进了代码**：

1. **机制码必须按属性配对，不能全笛卡尔积**。一个战法同时挂 `attack_buff` 与 `defense_buff`，
   两个槽位各对应一半；按「buff 类型 → 机制码」表（`ATTR_CODES`）配对后，码表分布**全部落在主对角**
   （101→attack、102→defense、103→strategy、104→speed、201-204 同理），零假配对。
2. **符号要参与比较**。武锋「攻击、谋略 −56」包内 `c=4000 / i=4000` → 56 点，引擎 `amount: -56`；
   按绝对值比会把「提高写成降低」的符号错误一起放过。
3. **必须成组对齐**。同一个属性在包内可能有多条槽位（坚守兵法 `20062001` i=7000 → 28 点、
   `20062012` i=2100 → 8.4 点），引擎只写一条；逐条硬比会拿 8.4 去比 28 造出假差异。
   槽位数 ≠ 引擎同类 output 数时一律 `ambiguous` 跳过 —— 宁可漏判，不造假差异。

**扩映射结果**：可判 **228 条（37.3% → 50.0%）**、一致 **104**（原 76）、差异 **9**（已全部修复，见上文「真差异」表）。
新增 3 条差异全部同型 —— **引擎侧属性增减没写 `growthRate`**（包内给了成长率）：

- `献刀七星` 槽 `20004202`（204 速度降低）包内成长 **0.1**，引擎 `amount: -28` 无 `growthRate`（`src/data/skills.ts:885`）
- `筹策绝道` 槽 `20095302`（203 谋略降低）、`20095303`（204 速度降低）包内成长 **0.11**，
  引擎 `amount: -25` 无 `growthRate`（`src/data/skills.ts:2474-2475`）

加上原有的金匮要略（0.13 vs 0.18）与将倾之柱（0.175 vs 未写），**7 条差异全部是成长率问题**，
指向同一个系统性模式：引擎在写属性 / 减伤增减时普遍省略 `growthRate`，等于把随属性成长当成了常数。
值本身全部一致 —— 单位换算没有错，缺的是成长维度。

**为什么还剩 50%**：未映射的机制码集中在**子技能引用**（122，1,947 条，值就是另一个 `skill_id`，
不是数值）、**受兵种伤害**（98/99 共 2,565 条，引擎无对应字段）、触发 / 移除（151/152）、标记（77）。
前者属「关系」不是「数值」，需要另一套比法（子战法递归），后几类引擎尚未建模。

## 六、附：本次对拍修掉的对齐 bug

初版 `alignHeroes` 只按指纹 + heroid 最小，报出 6 条「差异」，其中 5 条是 SP 版错配到普通版造成的假差异。
加入 id 直配与主战法名定序后，假差异全部消失，真实差异收敛到 1 条。
`diffSkill` 初版把「包内→引擎」换算值放到了 engine 位置（参数写反），导致类型差异 100% 误报；修正后类型差异从 4 条降到 2 条。

教训：对拍工具本身要先自证 —— 任何「差异率异常高」都应先怀疑对齐与口径，而不是先怀疑数据。

槽位对拍同一课又来了一遍：首版 `SLOT_MAP` 把减伤的换算系数写成 ×100（真值应 ×0.01），
报出 `包内 4900 ≠ 引擎 0.49`、`包内 8000 ≠ 引擎 80` 一类的荒谬值 —— 一眼就能看出是换算错，不是数据错。
**所以对拍结果里出现「量级差 100 倍」时，先查 scale，别写进报告。**
