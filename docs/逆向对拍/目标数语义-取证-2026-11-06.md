# 「敌军群体（有效距离内 2-3 个目标）」到底是什么机制 —— 包内取证

> 起于用户提问：*「部分战法目标选择是敌军群体 2 到 3 目标，2 目标和 3 目标分别是对应的概率是多少？目前引擎只是单纯的各占一半概率，这只是凭感觉估算的」*
> 数据源：`C:/Users/lai15/Desktop/rea_stzb/hot_20261104/json_latest`（11-04 热更，P0）。引擎侧对照：`src/engine/target.ts`、`src/data/skills.ts`（P1）。

## 一、结论（三句话）

1. **包内不存概率，存的是区间。** `tb_cfg_skill_detail` 用 `select_type` + `attack_max` 两个字段编码目标数：`select_type = 32 + 下限`（33→下限 1、34→下限 2），`attack_max` = 上限；`select_type=0` 表示「恰好 attack_max 个」。**没有任何字段承载「2 个 vs 3 个各多少概率」**（逐字段排除见 §四）。
2. **计数在区间内是随机的，不是「有效距离内有几个就打几个」。** 反证：炬石（200085，距离 4）的官方标签是「有效距离内 **1-3** 个目标」，而距离 4 的战法在 3v3 里几何上最少也能覆盖 2 名敌人（大营施法 2 人、中军/前锋施法 3 人），**永远不可能只覆盖 1 个** —— 只有当计数是从 `[下限, 上限]` 里随机取时，「1-3」才可能出现。
3. **区间内的权重包内没有证据**（逐字段排除见 §四）；`select_type=34` 的实际取值按**实测口径**：**2 目标 2/3、3 目标 1/3**（用户 2026-11-06 转达，非包内字段）。`[1,2]` / `[1,3]` 两类仍未实测，引擎按闭区间均匀取。

## 二、字段语义（P0）

| `select_type` | 语义 | `attack_max` | 官方 `target_description` |
|---|---|---|---|
| 0 | 恰好 N 个（N 不足时全取） | N | `敌军群体（有效距离内3个目标）` / `敌军全体` |
| 33 | `1 .. N` | N | `敌军群体（有效距离内1-2个目标）` / `（有效距离内1-3个目标）` |
| 34 | `2 .. N` | N（恒为 3） | `敌军群体（有效距离内2-3个目标）` |
| 9 | 按某属性最高/最低选人 | — | 非目标数语义（`select_attri` 标属性） |

注意 `tb_cfg_skill.target_description` 对 **6375 / 6634** 条战法都是占位 `"0"`，所以「目标类型」文案是**少数手写**、多数由客户端按枚举渲染；手写的那批（铁戟金戈、河内世泽、兵行巧变…）出现 `2-3` 但 `select_type=0` 的情形，是因为它们用**两个槽位分支**实现「2 个 or 3 个」（见 §五）。

## 四、为什么「概率」查不到（逐字段排除）

对 `select_type ∈ {0, 33, 34}` 三组分别做全字段透视（12,189 / 88 / 113 行）：

- `prob_init_param` / `prob_max_param`：33/34 组内 100:83 / 50:3 / 40:2 等 —— 是**效果生效几率**（如燃烧每回合触发率），与目标数无关；
- `prob_series`：33/34 组 **113/113 全空**；非空仅出现在 `select_type=0` 的 11 行，内容是 `"133,167,200,233,267,300,334"` / `"88,75,63,50,38,25,13"` 这类**伤害率序列**（随等级/回合变化），不是计数权重；
- `custom_select_flag` / `select_attri`：33/34 组 **全部为 0**；
- `select_flag`：33/34 组全 0（非 0 仅出现在 `select_type=0` 的 366 行）；
- `display_param`：是**特效类型**（3=火、5=水、6=单体…，焰焚箕轸/火箭/火辎=3，绝水遏敌/水淹七军/溃堤=5），不是展示档位；
- 机制字典 `tb_cfg_skill_effect`（205 条）里与目标数相关的**只有 117「战法目标数提升」**，没有「目标数随机」「目标数下限」之类的机制；
- `tb_cfg_skill_effect_map` / RAG 语料里也没有相关条目。

## 五、包内如何表达「2 个 or 3 个」

铁戟金戈（200833 / 300061）是最好的一面镜子：官方描述「对敌军群体 **2 目标** 发动一次猛烈攻击（伤害率 330%）**或** 对敌军全体 **3 目标** 发动一次…（伤害率 225%）」，表里对应**两个独立槽位**：`20083301`（`select_type=0`、`attack_max=2`、const 330）与 `20083312`（`select_type=0`、`attack_max=3`、const 225）。

⇒ 需要「两档概率各带不同数值」时，策划用**双槽位分支**表达；而单槽位的 `select_type=34` 是「一份数值、目标数在区间内浮动」。这反过来印证 §一.2：区间浮动是运行时随机的，否则 34 与 0（全体）在数值模型上无法区分。

`node scripts/_audit_target_count.mjs` 把引擎里 74 个带 `groupCount` 的战法与包内槽位逐条并排打印，**区间全部对得上**（抽样）：

⇒ **数据形状是对的**；区间内的取值权重见 §七（`[2,3]` 已按实测改成 2:1）。

## 七、区间内权重：`[2,3]` = 2/3 : 1/3（实测），其余仍均匀

- **已定（实测口径，非包内）**：`select_type=34`「有效距离内 2-3 个目标」中，**2 目标 2/3、3 目标 1/3**。来源为用户 2026-11-06 转达的实测结论（有人在游戏内统计）；包内 5 张表没有任何字段承载这组权重（§四逐字段排除），因此这是**唯一非包内来源的数值**，落库时必须标注来源。
- **落点**：`src/engine/target.ts` 的 `GROUP_COUNT_WEIGHTS = { '2,3': [2, 1] }` + `rollGroupCount()`（按权重抽，恰好消耗一次 `rng.next()`，可复现序列稳定）；期望模型走 `expectedGroupCount()`（`[2,3]` → 2.333），`web/roundModel.ts` 的 `targetCount()` 已改为复用它，避免期望值仍按中点 2.5 高估约 6.7%。
- **未定**：`[1,2]`（st=33：十面埋伏减伤段 / 翕处还张次段 / 休整 / 定军扬威…）与 `[1,3]`（炬石）区间内的权重（均匀？偏上限？）。包内给不出，客户端程序集里也没有选人算法（`Game.Data.GamePlay` 只有战报播放类，`libEngine.Native.dll.so` 为无符号原生库且 `strings` 无相关常量），实测样本也还没有。
- **可继续定的两条路**：① 服务端/原生层反编译定位选人函数（成本高、当前环境无符号）；② 真实战报样本统计 —— 统计「3 名敌人全在有效距离内」时目标数 1 vs 2（st33）与 2 vs 3（st34）的频次（≥200 次即可分辨 50/50 与 2:1 这类差异）。
- 未登记权重表的区间一律走**闭区间均匀**（最大熵假设），新增实测数据时只需往 `GROUP_COUNT_WEIGHTS` 加一行。
