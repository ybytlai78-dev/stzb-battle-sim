# 战斗诊断工具（贡献排名 → 因果归因）

> **一句话**：把战报里的「谁打了多少」升级成「**为什么是这个数**」——
> 只读引擎既有事件流，**不新增埋点、不改战斗逻辑、不重跑引擎**，输出每个增减伤/克制/控制的**绝对伤害贡献**、
> 主战法空转的可识别证据、技能顺序缺口的证据与估算损失，最后给出**主因排序**的结论。

- 代码：`src/engine/diagnosis.ts`（分析）+ `src/engine/diagnosisReport.ts`（文本渲染）+ `scripts/diagnose.mts`（CLI）
- 测试：`tests/diagnosis.test.ts`（20 例）
- 版本：`DIAGNOSIS_VERSION = 1.0.0`（随输出携带）

---

## 1. 定位与数据来源

| 项 | 说明 |
|---|---|
| 输入 | `BattleReport`（含 `events` 事件流）：单场或一批 |
| 唯一数据源 | 引擎既有事件流（`damage` / `attack_hit` / `dot_tick` / `split_damage` 的 `modifiers`、`status_inflicted` / `status_expired`、`skill_trigger` / `skill_cast` / `prepare_*`、`unit_act_start` / `unit_act_end`、`round_*`、`no_attack_target` 等） |
| 不做的事 | 不新增事件字段、不改 `combat.ts` / `action.ts` / `types.ts`、不重新模拟、不做反事实重跑 |
| 只读保证 | ① 诊断函数不改动传入战报（测试断言 JSON 逐字节一致）；② 战斗主循环未引用诊断模块（测试读源码守卫）；③ 纯离线分析，线上战斗零开销 |
| 允许的只读引用 | `src/engine/stats.ts`（复用贡献排名口径）、`src/engine/secondaryTroop.ts` 的 `troopCounterReduceOf`（算「应交克制」）、`src/data/skills.ts` 的 `SKILL_REGISTRY`（读战法名/类型/标签） |

## 2. 使用方式

```bash
# ① 单场（战报 JSON 文件）
npx tsx scripts/diagnose.mts 战报.json

# ② 一批（文件 / 目录都行，目录递归收集 *.json）——批量模式
npx tsx scripts/diagnose.mts reports/ --json out/diagnosis.json

# ③ 免文件：内置测试集跑批（同队多次 → 共性问题）
npx tsx scripts/diagnose.mts --fixture T7_LOADOUT --runs 20

# ④ 免文件：跨阵容对照（差异因子）
npx tsx scripts/diagnose.mts --fixture T7_LOADOUT,T9_COMMAND_MECHANICS_L40 --runs 15

# ⑤ 顺手导出原始战报（供 ② 复用 / 给别人诊断）
npx tsx scripts/diagnose.mts --fixture T7_LOADOUT --runs 3 --dump-reports tmp-reports
```

也可用 npm 脚本（等价）：`npm run diagnose -- --fixture T7_LOADOUT --runs 10`。

**接受的 JSON 形状**（自动识别）：单个 `BattleReport`、`BattleReport[]`、
Web 战报历史的 `BattleRecord[]`（形如 `[{ report: BattleReport, … }]`）、`{ report }` / `{ reports: [] }`。

**参数**

| 参数 | 作用 |
|---|---|
| `<路径…>` | 战报 JSON 文件或目录（可多个） |
| `--fixture A,B` | 跑内置测试集（逗号分隔），免文件 |
| `--runs N` | 每个 fixture 跑 N 场（换种子），默认 1 |
| `--json <out>` | 导出结构化诊断（单场 = `BattleDiagnosis`；多场 = `{ batch, reports }`） |
| `--dump-reports <dir>` | 把原始战报落盘（供文件模式复用） |
| `--quiet` | 只输出 JSON/导出信息，不打文本报告 |

**编程调用**

```ts
import { diagnoseBattle, diagnoseBatch } from './src/engine/diagnosis';
import { diagnosisToText, batchDiagnosisToText } from './src/engine/diagnosisReport';

const d = diagnoseBattle(report);                 // 单场
console.log(diagnosisToText(d));
const b = diagnoseBatch([{ report: r1 }, { report: r2, label: '对照组' }]);  // 批量
console.log(batchDiagnosisToText(b));
```

**批量口径（自动识别，两类一起给）**
- **同阵容共性问题**：按队伍指纹（我方+敌方武将、槽位战法、等级）分组；组内场次 ≥ `batchMinReports`(3) 才统计，
  某类病灶在 ≥ `batchCommonSharePct`(60%) 的场次出现 → 报为共性问题（带组内均值）。
- **跨阵容差异因子**：取「每回合伤害」最高/最低两组做逐因子对照，`方向` 列标出该因子到底**谁占优**
  （`低分组反而占优` 的因子不会被当成高分组的优势），并在结论里只列「高分组占优」的因子。
  这是**相关对照，不是因果证明** —— 输出里显式标注。

## 4. 指标口径（逐条给公式与分母）

### 4.1 因果账本（核心）

引擎在每条伤害事件上带 `modifiers`（`caused` / `taken` / `reduce` 三个方向 + 数值），
且结算口径是**单一总和模型**（`src/engine/formulas.ts` 的 `buffMult`）：

```
m        = clamp(1 + Σcaused + Σtaken − Σreduce, 0.1)
基线      = (base + main) / m              // base/main 取事件 breakdown（已含 m），故反解即「无增减伤时应有多少」
来源贡献_i = 基线 × rate_i × (direction === 'reduce' ? −1 : +1)
```

- 账本只作用于 `base + main` 分量；**兵力基础（`troopBase`）不参与增减伤**，单独列出以便核对。
- **触底**（净额 ≤ −90%，实际按 10% 结算，如辕门射戟 −99.99%）：各来源贡献按比例缩放，保证 Σ贡献 = 实际 − 基线，
  并在输出里标 `触底事件 N 条`。
- **截断**（`applyTroopCap` 按目标剩余兵力截断 / 最小 1 点）：按比例折算，输出里标 `兵力截断损失`。
- **无归因路径**：事件**没有** `modifiers` 字段时（一类指挥预存 `delayedOutput`，预先结算不吃增减伤）计入
  `unattributed`，不进账本。⚠️ 带**空** `modifiers` 数组 ≠ 无归因，那是「本次没有任何增减伤/克制」（m=1）。
- **闭合自检**：输出 `Σ来源贡献 −（可作用分量 − 基线）`，正常为 0（浮点/四舍五入容差 ±1）。
- 来源条目按 `(方向, 战法)` 合并，`施加者/受击方` 列给出各单位拆分；
  **兵种克制的拆分单位取「被克的攻击方」**（引擎写入的 `unitId` 是受击方，对诊断没意义）。
- DoT（`dot_tick`）用的是**挂上时冻结**的 modifiers → 同样进账本（归到挂上那一刻的增减伤）。

### 4.2 增益 / 减益覆盖率

| 量 | 口径 |
|---|---|
| 施加次数 | 该侧单位身上 `status_inflicted` 的条数（按 `statusType` 归类） |
| 覆盖单位回合 | 该侧每个「行动窗口」的**行动开始时刻**（`actStartIdx`：本行动首个 `unit_act_start` / `no_attack_target`），该状态是否处于生效中（`startIdx < 采样点 ≤ endIdx`） |
| 分母 | 该侧**有行动窗口的单位回合数**（阵亡/未行动的不计入） |
| 覆盖率 | 覆盖单位回合 ÷ 分母 |
| 平均持续 | 状态区间跨越的回合数均值（`status_inflicted` → `status_expired`，未结束算到战斗结束） |
| 推定来源 | 该状态事件前最近的 `skill_cast` / 成功的 `skill_trigger` / `prepare_start/end`（同一行动窗口或同一回合、≤8 事件距离）；被动直接挂的状态（如击势）**没有释放事件** → 来源留空，不会被瞎猜 |

**增益/减益判定**：`STATUS_META` 给基础类别，再按状态文本修正（`damage_boost` 看「造成的/受到的」与提高/降低；
属性类看「提高/下降」）。

### 4.3 控制

| 量 | 口径 |
|---|---|
| 被控回合数 | 该单位本回合**行动开始时刻**带着控制状态（混乱/暴走/怯战/犹豫/挑衅）的回合数 |
| 被控占比 | 被控回合数 ÷ 该单位有行动窗口的回合数 |
| 流失判定机会 | 被控回合中，若该将是主动战法（混乱/犹豫封禁）或追击战法（混乱/怯战封禁）→ 计 1 次 |
| 施加控制覆盖 | 从对手视角：其行动回合被你方控制覆盖的回合数 ÷ 其行动窗口数（施加者由 4.2 的来源推定；推不出来的单独计数，不计入） |
| 事件佐证 | `no_attack_target`（混乱/怯战原因）、`insight_blocked`、`control_immune_blocked`、`cowardice_immune_blocked`、`status_resisted` |

### 4.4 兵种克制（被克 30% 这类数值的实际生效情况）

- **应交**：用引擎自己的 `troopCounterReduceOf`（含二级兵种改写、长枪兵反克）算出每一对（攻击方 → 目标）的克制减伤率，
  `> 0` = 攻击方被克，`< 0` = 攻击方反而增伤。
- **实交**：该方向每条伤害事件的 `modifiers.reduce` 里是否带 `skillId = 'troop_counter'`。
- **合规率** = 实交 ÷ 应交；不合规的按原因分桶（战法自带「无视兵种相克」/ 预存或特殊路径）。
- **影响量** = 账本里该条 `troop_counter` 贡献之和（正 = 少打，负 = 多打），并按「被克的攻击方」拆分。

### 4.5 技能顺序缺口（是否出现顺序导致吃不到增伤）

判定规则（只用事件顺序 + 引擎自己的结构化归因，不猜战法名）：

1. 取一个行动窗口，找出窗口内**后施加**的增减伤状态（`damage_boost`，作用于该将 = `caused`，或作用于其目标 = `taken`），
   数值从状态文本解析；
2. 该增伤的来源：优先近邻释放事件；否则用**同窗口后续伤害事件自己的 `modifiers`** 反查（同方向 + 同数值 → 取那里的 `skillId`）——
   即「同一行动里别人吃到过这个增伤」，来源可考；
3. 窗口内**早于**该施加时点的、由该将打出的伤害（普攻/战法/分兵；DoT 排除，它是挂上时冻结的），
   若其 `modifiers` 里没有这个来源 → **顺序缺口**；
4. 估算少打 = `(base + main) × rate`（受截断按比例折算），标 `实证`（来源与数值都有事件依据）。

`scope`：`self` = 同一武将自身槽位顺序（例：孙策【霸王渡江】槽 1 早于【击势】槽 2）；
`sameWindow` = 同一行动窗口内他人/后续效果给出。

> 局限：`ignore_def`（无视防御）**不进**顺序缺口判定 —— 它不出现在 `modifiers` 里，无法自证；
> 但引擎里它与增伤同寿，因此「增伤缺口」通常同时意味着无视防御也没吃到（输出只报可证的部分）。

### 4.6 主战法空转（可识别证据）

对每个武将的 `general.mainSkillId`：

| 量 | 口径 |
|---|---|
| 释放次数 | `skill_cast` 计数；被动/指挥这类**没有释放事件**的，改按「有效生效回合」计（输出标 `按生效回合计`） |
| 判定次数 / 失败 | `skill_trigger` 计数与 `success=false` 计数；实际发动率 = 释放 ÷ 判定 |
| 准备 | `prepare_start` / `prepare_skip`（跳过准备）/ `prepare_end(success=false)`（准备失败中断） |
| 被控跳过 | 本回合行动开始时被控制，且该战法类型会被封（主动 ← 混乱/犹豫；追击 ← 混乱/怯战）→ **单列，不计入空转** |
| 准备中 | 登记了准备槽且本回合未释放 → **单列，不计入空转** |
| 空放 | 该回合有 `skill_cast` 但没有任何伤害/恢复/状态产出；证据行会进一步取证原因（同行动内出现「被规避 / 效果冲突被拒 / 被抵御 / 被围困拦截 / 被免疫拦截」就照实写，取不到就写「无新增效果（目标已有效果 / 无有效目标）」） |
| 有效生效回合 | 该战法在该回合产生了伤害 / 恢复 / 状态（限制在该将确实行动的回合内，DoT 滞后跳伤不虚增） |
| **空转回合** | `行动回合 − 有效生效回合 − 被控跳过 − 准备中`（下限 0） |
| 空转率 | 空转回合 ÷ 行动回合 |
| 一次性战法 | 一类指挥（`phase:'prep'`）/ 纯 `battle_start` 被动 → 不适用每回合口径，空转记 0（输出 `·一次性`）；**混合型**（如霸王渡江：battle_start 挂犹豫 + 每回合 40% 三连击）仍按每回合口径 |
| 证据 | 逐回合人话：「第 N 回合发动判定失败（生效几率 40%）」「第 N 回合被控制跳过」「第 N 回合释放但零效果」「第 N 回合处于准备中（不计空转）」 |

### 4.7 归因结论（回答「伤害差异到底是哪个」）

四个候选因子，各自给出**估算影响量**与**证据数**，按影响量排序：

| 因子 | 影响量算法 | 置信度 |
|---|---|---|
| 兵种克制 | 我方被克账本损失 − 敌方被克账本损失 | **实证**（账本条目） |
| 技能顺序 | 我方顺序缺口估算少打 − 敌方 | **实证**（来源与数值有事件依据） |
| 主战法空转 | 我方 Σ(空转回合 × 该将主战法每有效回合均伤) − 敌方 | 估算 |
| 控制覆盖 | 我方 Σ(被控流失判定机会 × 每有效回合均伤) − 敌方 | 估算 |

- 空转与控制**互斥计数**（被控跳过不算空转），所以两项不会重复计同一回合。
- `primary` = 影响量为正且最大的因子；全为 0 → `none`（并说明四类都无正影响）。
- 输出同时给**伤害对比**（我方 vs 敌方、差额、百分比）。

## 6. 局限与已知边界

1. **状态区间是事件回放重建的**：同单位同类型多个实例时按 FIFO 配对 `status_inflicted` / `status_expired`；
   引擎个别路径直接改状态而不发 `status_expired` 时，区间会延到战斗结束（覆盖率偏高）——属于“宁可少报不误报”的取舍。
2. **状态来源是「推定」**：引擎的 `status_inflicted` 事件不带 `sourceSkillId`，被动直接挂的状态（如击势）没有释放事件，
   只能靠近邻事件或（顺序缺口里）用后续伤害的 `modifiers` 反查。账本与克制归因**不依赖**这个推定（走结构化 `modifiers`）。
3. **顺序缺口只覆盖 `damage_boost`**：`ignore_def` 不在 `modifiers` 里，无法自证，未纳入判定（§4.5）。
4. **空转/控制的损失是估算**：用「每有效回合均伤」当单价，不等于真实反事实重跑（本工具按需求约定不重跑引擎）。
   输出里所有估算都标了 `估算`，实证的标 `实证`。
5. **伤害差异的解读以我方视角**：`Verdict` 的四个影响量都按「我方 vs 敌方」的差值给，正 = 对我方不利。
6. **不要拿它当胜率工具**：它解释伤害与效果，不预测胜负；批量模式的相关对照也不能当因果证明（输出已标注）。
