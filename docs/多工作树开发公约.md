## 一、三棵树与职责

| 目录 | 分支 | 管什么 | 对应方向 |
|---|---|---|---|
| `.wt-stzb/engine` | `feat/engine-fix` | 既有引擎**行为错误**的修复（bug、口径不一、边界） | ② 战斗引擎修复 |

## 三、`src/engine/**` 的串行节奏

engine 树与 mechanic 树都会动 `src/engine/`。纪律：**任一时刻 `src/engine/` 的写入权只有一棵树**。

- engine 树改引擎 → **一个小改动一次提交，立刻合回 main**；
- mechanic 树在动手补机制前 `git rebase main`，拿到的就是最新引擎；
- mechanic 树改引擎（新增机制）→ 同样小步高频合 main；engine 树随后 rebase。

理想批次：一个机制 = 一次提交 = 一次合 main。不要把引擎改动攒成大礼包。

## 四、生成物纪律（**最重要，直接消掉最大的冲突源**）

以下文件的改动**一律不在分支里提交**，只在 main 上重建：

```
web/data/heroes.json
web/data/skill_grades.json
web/data/skill_desc.json
tests/__snapshots__/golden.json
scripts/seed_heroes.sql
```

分支里为了让 `npm test` 绿，**可以**本地跑生成脚本，但提交前执行：

```bash
git restore web/data/ tests/__snapshots__/ scripts/seed_heroes.sql
git status --short      # 应只剩源码与测试文件
```

理由：这三个 JSON 是**全量重生成**产物，两份分支各跑一遍 = 整文件 diff，文本合并必然爆炸；`golden.json` 单个 570KB，且仓库规则**禁止盲刷**（须走 `scripts/compare-golden-snapshot.py` 证明只有文案漂移）。

## 五、合并流程（固定顺序）

合并顺序固定：**engine → mechanic → growth**（引擎先稳，机制再消费，数据最后）。

```bash
# 在 main 工作区
git checkout main
git merge --no-commit --no-ff feat/<branch>      # 或 --squash
# 生成物一律以 main 版本为准，丢弃分支的生成物改动
git checkout HEAD -- web/data/ tests/__snapshots__/ scripts/seed_heroes.sql
npm test                                          # 分支源码 + main 生成物
# 合并后重建生成物（此步在 main 完成）
node scripts/build_heroes_seed.mjs
node scripts/gen_skill_data.mjs
node scripts/export_web_data.mjs
npx tsc --noEmit && npm test
npx vitest run tests/golden.test.ts               # 如需更新快照，先跑比对器
git add -A && git commit
```

## 六、数据库隔离（已落地）

**决策（2026-09-16，用户拍板）**：三路并行前先做隔离 —— 抽 `scripts/db-config.mjs`，每棵树一个独立库。

**为什么必须做**：`src/data/heroes.ts` 的 `initHeroDB()` **优先连 MySQL**，连不上才回退 JSON。而三棵树原本共用主库，growth 树一跑 `seed_db` 就会让 engine/mechanic 树的 40 级面板集体漂移 → `golden` 与数值断言红，而它们代码没动。这种跨树污染极难定位。

**实现**：

- `scripts/db-config.mjs` 统一解析连接参数：优先环境变量（`STZB_DB_HOST` / `STZB_DB_PORT` / `STZB_DB_USER` / `STZB_DB_PASSWORD` / `STZB_DB_NAME`），其次按**树根路径自动推导** —— 树根形如 `.wt-stzb/<name>` → 库名 `stzb战斗系统_wt_<name>`，否则主库 `stzb战斗系统`。
- `src/data/heroes.ts` 的 `DEFAULT_DB_CONFIG` 内置同一套推导。⚠️ **tsconfig 的 `include` 不含 `scripts/`，无法直接 import，所以两边各写一份 —— 改一处必须同步另一处**。这是**测试真正走的路径**，只改 `scripts/` 下的 .mjs 是无效功。
- `initHeroDB` 回退条件新增 `ER_BAD_DB_ERROR`：工作树库未建时自动回退各自的 `web/data/heroes.json`（带 `console.warn`），不会把测试直接炸掉。

| 树 | 库名 |
|---|---|
| main | `stzb战斗系统` |
| engine | `stzb战斗系统_wt_engine` |
| mechanic | `stzb战斗系统_wt_mechanic` |
| growth | `stzb战斗系统_wt_growth` |

**建库 / 刷新**：`ybyt@localhost` 只有主库的 ALL 权限，**建库必须 root**。做法见 skill `stzb-battle-engine-dev` 的 `scripts/init-worktree-dbs.mjs`（`--create <root密码>` 建库授权、`--seed` 复制主库结构与数据，均幂等）。

**日常纪律**（隔离完成后不再需要串行）：

- 每棵树的 `seed_db` / `export_web_data` / `seed_universal_skills` 自动读写**自己的库**；
- `build_heroes_seed.mjs` 与 `gen_skill_data.mjs` 不连库，随便跑；
- ⚠️ **合并到 main 后必须在 main 重跑一次数据链**（`build_heroes_seed → seed_db → export_web_data`），把三棵树的成长率/挂槽改动汇进主库，否则主库与仓库数据源会脱节。

## 七、端口与本地验收

vite 默认 5173，三棵树同时起会抢端口：

| 树 | 命令 |
|---|---|
| engine | `npm run web:host` （5173） |
| mechanic | `npx vite --host --port 5174` |
| growth | `npx vite --host --port 5175` |

线上部署（`bash scripts/deploy-gh-pages.sh`）**只在 main 工作区执行**。

**⚠️ 并发跑测试会 flaky（实测）**：三棵树同时跑全量 `npm test` 会互抢 CPU，`web/smoke.test.ts`（jsdom 渲染冒烟）实测出现 1/20 随机失败，而**单独重跑该文件 20/20 全绿**。

诊断口径：看到树里有零散失败（尤其 `web/smoke.test.ts`）时，**先单独重跑那个文件**——绿 = 负载 flaky，红 = 真问题，别急着怀疑代码。要并发跑就给 vitest 限并发（`npx vitest run --no-file-parallelism`），或干脆让三棵树错开时间跑全量测试。

## 八、上下文隔离怎么落

工作树隔离的是**文件系统**，不隔离上下文。要拿到干净的上下文：

- 每棵树配一个独立的 Hermes 桌面 Project（workspace 指向 `.wt-stzb/<name>`），开新会话时选中对应 project；
- 该会话的 `AGENTS.md`（仓库内随树带一份）与探索轨迹互不污染；
- 不要在一个会话里跨树操作。

## 九、叫停时的交付姿态（沿用仓库既有规则）

用户叫停时停在**已验证、未提交**状态，交付四件套：改前/改后对照表 · `npx tsc --noEmit` ＋ `npm test` 实测结果 · **显式列出未做的项** · `git status --short` 待提交清单。不擅自提交、不擅自接着做下一项。
